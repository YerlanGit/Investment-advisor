## 1. Почему измерений здесь нет — и почему это не «не успели»

Два независимых препятствия, оба перепроверены **2026-08-06**, а не взяты из
плана:

**1. Сеть.** Агентское окружение не пускает к Stooq:

```
$ curl https://stooq.com/q/d/l/?s=aapl.us&i=d
curl: (56) CONNECT tunnel failed, response 403
$ curl https://stooq.pl/...
curl: (56) CONNECT tunnel failed, response 403
```

Тот же 403 отдаётся на `tradernet.com` — политика окружения, а не сбой Stooq.

**2. Ключ.** `STOOQ_API_KEY` в окружении отсутствует и получить его отсюда
нельзя: эндпоинт вместо CSV возвращает инструкцию открыть
`https://stooq.com/q/d/?s={ticker}&get_apikey` и ввести **капчу**
(`PHASE_08 §0`). Это принципиально не автоматизируется.

**Что из этого следует для читателя.** Любая таблица покрытия, заполненная без
этих двух условий, была бы выдумана. Значения ниже помечены `НЕ ИЗМЕРЕНО`
намеренно — пустая ячейка честнее правдоподобной. Фаза 08 закрывается
оператором, а не агентом; агент подготовил всё остальное.

### 1.1 🟢 Обновление 2026-08-09: оба препятствия обходятся выгрузкой

Владелец обнаружил `https://stooq.com/db/` — история скачивается **целиком,
без API**. Препятствия при этом не «исчезли», а перестали относиться к замеру:

| | было (API) | стало (bulk) |
|---|---|---|
| Капча | блокирует замер | ключ не нужен вовсе |
| 403 на CONNECT | блокирует замер | нужен ОДИН ручной скач, дальше офлайн |
| Кто выполняет | оператор в сетевом окружении | оператор скачивает файл, замер — где угодно |

Проверено 2026-08-09: `stooq.com/db/`, `stooq.com/db/h/`, `stooq.pl/db/` —
по-прежнему `403` из этого окружения, поэтому скачать архив агент не может;
но всё, что идёт ПОСЛЕ скачивания, теперь автоматизировано и покрыто тестами.

## 2. Как заполнить

### 2a. 🟢 Рекомендуемый путь — BULK-выгрузка (ключ НЕ нужен)

Находка владельца 2026-08-09: `https://stooq.com/db/` отдаёт историю **целиком
одним архивом, без API**. Оператору нужен браузер и одна команда; сама
процедура замера идёт **офлайн**, поэтому ни капча, ни сетевая политика её
больше не блокируют.

```bash
# 1. скачать пакет(ы) браузером со https://stooq.com/db/
# 2. замер — БЕЗ сети:
PYTHONPATH=src python scripts/stooq_coverage_probe.py \
    --dump ~/Downloads/d_us_txt.zip --dump ~/Downloads/d_world_txt.zip \
    --out docs/audit/STOOQ_CONVENTION.md
```

Скрипт принимает и `.zip`, и распакованный каталог, ищет бумагу по **имени
файла** (раскладка каталогов у выгрузки своя и заранее неизвестна) и
**определяет формат сам** — шапку, разделитель, формат даты, — после чего
докладывает наблюдённое в §4. Формат нигде не зашит: живого архива у автора
скрипта не было, а утверждать формат по памяти — это ровно ошибка E-4.

🔴 **Перед включением в проде проверить условия использования страницы `/db/`.**
Массовое скачивание базы — другой по объёму акт, чем разовый запрос котировки, и
регулируется отдельно. `PHASE_09 §3.2` уже фиксирует, что условия программного
доступа не проверялись; для bulk этот вопрос **весомее**, а не легче.

### 2b. Запасной путь — API по тикеру (нужен ключ через капчу)

```bash
STOOQ_API_KEY=<ключ> PYTHONPATH=src \
    python scripts/stooq_coverage_probe.py --out docs/audit/STOOQ_CONVENTION.md
```

### 2c. Что проверяется — видно без сети и без файла

```bash
PYTHONPATH=src python scripts/stooq_coverage_probe.py --dry-run
```

Скрипт печатает таблицу «тикер → найден как → наблюдений → период → вердикт» и
возвращает код 1, если не покрыт хотя бы один факторный ETF (стоп-фактор §5).

**Список бумаг замера собирается ИЗ КОДА, а не из этого документа.** Держать
его markdown-таблицей нельзя: за две недели после написания `PHASE_08 §2.5`
список разошёлся с движком трижды —

| Что разошлось | План §2.5 | Код на 2026-08-06 |
|---|---|---|
| KZ/IL-бумаги | 4 (`kspi.kz`, `kap.il`, `hsbk.il`, `kztk.kz`) | **6** — добавлены `KMGZ.KZ`, `KEGC.KZ` (`§−70`) |
| Прокси | 5, `vwob.us` назван критичным | 5, из них **`VWO.US` не используется никем** (см. §7) |
| События сплитов | 3, у `googl.us` **неверная дата** (E-4) | **7** из `KNOWN_SPLITS`, даты из кода |

Дрейф закреплён тестами `tests/test_stooq_coverage_probe.py`: добавленный в
движок фактор или прокси попадает в замер автоматически.

## 3.2 ✅ Формат выгрузки — ИЗМЕРЕН 2026-08-09

Владелец скачал базу и прислал пять файлов (`zone.us`, `sss.us`, `spsc.us`,
`tph.us`, `vgit.us`). Читатель `--dump` распознал формат **с первого раза, без
правок** — обе гипотезы шапки оказались нужны, победила вторая:

```
<TICKER>,<PER>,<DATE>,<TIME>,<OPEN>,<HIGH>,<LOW>,<CLOSE>,<VOL>,<OPENINT>
ZONE.US,D,20240426,000000,4.01,4.24,3.1,3.5,1320880,0
```

| Свойство | Наблюдение |
|---|---|
| Шапка | ASCII-вариант (`<TICKER>,<PER>,…`), не «человеческий» CSV |
| Разделитель | `,` |
| Дата | `YYYYMMDD`, время `000000` (дневной интервал) |
| Имя файла | нижний регистр: `zone.us.txt`; тикер ВНУТРИ — верхний: `ZONE.US` |
| `<OPENINT>` | всегда `0` у акций/ETF |
| Глубина | до 16 лет (`vgit.us` с 2009-11-23, 4 197 наблюдений) — окно движка 1 260 покрывается с запасом |

### 3.3 🔴 Пять ловушек, каждая на своём файле

Пять присланных бумаг оказались пятью **разными** классами проблем. Это не
совпадение: так выглядит любая полная выгрузка рынка, и обработчик обязан
пережить каждую.

| # | Файл | Что в нём | Чем опасно |
|---|---|---|---|
| 1 | `tph.us` | последний close **2026-05-13**, возраст **88 дней** | 🔴 делистинг/остановка торгов. Ряд «есть», но мёртв. Без ПОТИКЕРНОЙ проверки свежести отчёт покажет трёхмесячные цены как текущие |
| 2 | `vgit.us` | объём **дробный**: `1824.5238176263` (3 274 строки из 4 197) | 🔴 загрузчик с `VOLUME BIGINT` упадёт или молча усечёт. Наш читатель объём не трогает, но провайдер Фазы 09 обязан знать |
| 3 | `sss.us` | 54 наблюдения, плотность **41 %** (торгуется не каждый день) | 🟡 ниже `MIN_OVERLAP_TDAYS=60` → sparse-guard движка её отбросит. Проверено: механизм уже работает, дыры нет |
| 4 | `spsc.us` | строка `20100421` с `OHLC = 6,6,6,6` и объёмом **0** | 🟡 синтетическая заглушка до IPO. Даёт день с нулевой доходностью в начале окна |
| 5 | `zone.us` | три обвала >33 % за день, худший −53 % (6.86 → 3.23) | см. §3.4 — самое интересное |

### 3.4 Эвристика сплитов на реальном обвале: запас **1 %**

`zone.us` — микрокап с обвалами, которые внешне неотличимы от сплита. Прогон
через НАСТОЯЩУЮ `_detect_and_adjust_splits` (а не через оценку):

```
2025-08-29 → 2025-09-02   6.86 → 3.23   raw=2.124   отвергнут, запас 0.010
2026-07-28 → 2026-07-29   0.70 → 0.3219 raw=2.175   отвергнут, запас 0.034
2025-11-07 → 2025-11-10   0.85 → 0.52   raw=1.635   отвергнут, запас 0.152
```

Ряд **не тронут** — гард `|log(snapped) − log(raw)| > 0.05` сработал как
задуман. Но порог принятия — `raw ≤ 2.103`, а ZONE дал `2.124`: **разошлись на
1 %**. Обвал на −52.6 % вместо −52.9 % переписал бы всю историю бумаги вдвое.

Честный вывод: защита есть и работает, запас на реальных микрокапах **тонкий**.
Это НЕ повод трогать её сейчас (правка эвристики меняет числа и на брокерском
пути), но повод замерить частоту таких скачков на полной выгрузке — там их
будут тысячи, и какая-то доля попадёт внутрь порога.

Отдельно: мой первый прогон был по УПРОЩЁННОЙ модели правила и дал «сплит
принят». Настоящая функция дала «отвергнут». Разница — в допуске 0.05,
которого в упрощении не было. Записано как напоминание: проверять надо тем
кодом, который поедет в прод, а не его пересказом.

### 3.5 Объём выгрузки — оценка по замеру

Средняя строка **64.8 Б**. Отсюда для полной выгрузки US:

| Что | Оценка |
|---|---|
| ~11 000 бумаг × 1 260 дней (окно движка) | ≈ **0.84 ГБ** распакованных |
| ~11 000 бумаг × ~3 000 дней (полная история) | ≈ **2.0 ГБ** распакованных |

🔴 На Cloud Run `/tmp` — это **RAM** при лимите 2 GiB. Распаковывать выгрузку
целиком в `/tmp` нельзя. Отсюда требование к Фазе 09: читать **члены архива
по одному**, не разворачивая zip (`DumpIndex` так и делает — `namelist()` не
инфлейтит содержимое).

## 3.6 🔴 Дневной срез `20260806_d.txt` — покрытие ИЗМЕРЕНО, и вывод неожиданный

Владелец скачал `d_us_txt` и прислал дневной файл со `stooq.com/db/`.
**701 КБ, 12 474 строки, та же шапка, переводы строк `CRLF`.**

### Что в файле на самом деле

Файл называется «дневным», но это **не только US и не только один день**:

| Класс | Строк | Комментарий |
|---|---:|---|
| US-акции | **8 408** | все с датой `20260806` — **100 % свежие** |
| JP-акции | 3 912 | здесь весь мусор: 43 строки с ПУСТОЙ датой, 148 строк старше августа (последний бар мёртвых бумаг, вплоть до 2015 года) |
| FX-пары | 95 | `EURUSD`, `XAUUSD`, кросс-курсы. `USDKZT` — **нет** |
| Мировые индексы | 59 | `^DAX`, `^NDX`, `^HSI`, `^MOEX`… |

Дублей тикеров нет. Для **US-части файл — идеально чистый срез одного дня**;
весь мусор сосредоточен в японской секции и отфильтровывается по правилу
«дата строки = дата файла».

### 🔴 Главное: в выгрузке НЕТ НИ ОДНОГО ETF

Проверка универсума движка по этому файлу дала 0 из 10 факторов. Причина
установлена — это **не отсутствие бумаг у Stooq, а состав пакета**:

| Проверено | Результат |
|---|---|
| 12 известных ETF (`SPY`, `QQQ`, `IWM`, `TLT`, `GLD`, `VOO`, `VTI`, `EEM`, `HYG`, `LQD`, `DIA`, `XLK`) | **все 12 отсутствуют** |
| 10 известных акций (`AAPL`, `MSFT`, `NVDA`, `TSLA`, `JPM`, `XOM`, `BRK-B`, `GOOGL`, `AMZN`, `META`) | **все 10 присутствуют** |
| Алфавит | полный `A.US` … `ZYME.US`, усечения нет |

Вывод: скачанный пакет содержит **акции США, без биржевых фондов**. А наш
универсум — это в основном ETF: 10 факторов, 3 бенчмарка и 5 прокси, итого
**18 из 34 бумаг замера**.

**Что нужно сделать:** докачать со `stooq.com/db/` пакет **ETF США**.
Без него `manual` не запускается вообще — C-1 в профиле `STRICT` даст BLOCK.

🟢 Это НЕ стоп-фактор запуска: бумаги у Stooq есть, их просто нет в этом
пакете. Вердикт группы A остаётся **неизвестным** до докачки — и записывать
его как «не покрыта» было бы ошибкой того же класса, что E-4.

### 🔴 Ловушка №6: `KSPI.KZ` «нашёлся» — но это другая бумага

Перебор форм символа дал совпадение `KSPI.KZ → kspi.us`, и оно **ложное по
смыслу**: `KSPI.US` в файле реален (close 91.8, объём 643 807) — это
американская ADR Kaspi на Nasdaq, а не листинг на KASE. Инструменты разные:
другая валюта, другая ликвидность, другой торговый календарь.

Запасной кандидат `{base}.us` в `stooq_candidates()` способен подобрать
однобуквенно похожую, но ЧУЖУЮ бумагу. Подстановка ADR вместо локального
листинга может быть осознанным решением — но именно **решением**, а не тихим
следствием перебора.

**Требование к Фазе 09:** формы символа, меняющие БИРЖУ, обязаны попадать в
отдельный список «подобрано с заменой площадки» и показываться на экране
подтверждения рядом с прокси-подменами. Молча — нельзя.

### Ответ на вопрос «можно ли обновлять базу этим файлом ежедневно»

**Да** — и это правильный способ. Обоснование и архитектура —
`manual_portfolio/PHASE_09_STOOQ_PROVIDER.md §9`. Кратко:

* файл маленький (701 КБ) и содержит ровно один бар на бумагу;
* US-часть на 100 % датирована днём файла, то есть готовая дельта;
* полная история качается **один раз**, дальше — только дневные файлы;
* правило фильтра ровно одно: **строка принимается, если её дата равна дате
  файла** — оно само отсекает и пустые даты, и последние бары мёртвых бумаг.

>
> `TradernetProvider` объявляет `SPLIT_ADJUSTED` не потому, что так отдаёт
> сервер (Tradernet конвенцию не документирует), а потому, что модуль сам

> молчат, поэтому сырой и уже скорректированный ряд дают побитово один
> результат, а повторный прогон не меняет ничего. Двойная корректировка,
> которой боялась `PHASE_08B §7.6`, **невозможна**.
>
> Значит `StooqProvider` объявляет `SPLIT_ADJUSTED` на том же основании, и
> замер ниже — не условие объявления. Он отвечает на два ДРУГИХ вопроса:
> попадают ли ступеньки Stooq в коридор ±20 %, который единственно и признаёт
> слой `KNOWN_SPLITS`, и наследуем ли мы ответственность за сплиты вне таблицы
> (у сырого ряда — да; дробный 3:2 стоит ровно на пороге эвристики).
>
> Строка «Дивиденды» остаётся НЕ ИЗМЕРЕННОЙ, и это честно ровно в той же мере,
> в какой она не измерена у Tradernet: там ответ «не `TOTAL_RETURN`» получен

## 6. 🔴 ЧК-08.2 — решение по непокрытым бумагам (принято ДО реализации)

Вопрос плана: «отказ, прокси или цена покупки». Ответ получен не рассуждением,
а **замером конвейера** — и замер вскрыл дефект.

### 6.1 Что происходит сегодня

Книга ручного ввода, где у одной бумаги нет ценового ряда (то есть ровно то,
что даст Stooq для непокрытого тикера):

```
введено          AAPL 20·150 · TLT 30·95 · GLD 20·180 · QQQ 10·400
                 IWM 15·200 · NOSTOOQ 100·500 · CASH:USD 5000
стоимость книги  $71 450, из них NOSTOOQ — $50 000 (70%)
───────────────────────────────────────────────────────────────
в отчёте         AAPL, GLD, IWM, QQQ, TLT, USD     ← NOSTOOQ НЕТ
total_value      $20 641                            ← вместо $71 450
чекеры           МОЛЧАТ
priced_at_cost   []      broker_priced_only  []     model_uncovered  []
```

**Позиция на 70% книги исчезает молча.** Отчёт строится по другому портфелю, и
ни одного признака этого в нём нет — ни в таблице, ни в реестрах раскрытия, ни
у чекеров качества.

Механизм (`portfolio_manager._stage_prices`): лестница цен имеет три ветки —
матрица, цена брокера, цена покупки **для проксированной** бумаги. Обычная
бумага без ряда не подходит ни под одну, `Current_Price` остаётся `NaN`, и
строку удаляет `dropna(subset=['Current_Price'])`. C-8 считает покрытие по
стоимости **уже выживших** строк, поэтому потерянные 70% для него не
существуют.

Почему это не видно на брокерском пути: `mkt_price` от Freedom ловит такую
бумагу второй веткой. У `manual` цены брокера нет **по определению**, поэтому
непокрытие Stooq — не край, а штатный исход.

### 6.2 Решение

| Вариант | Решение | Обоснование |
|---|---|---|
| **Прокси** | ❌ отвергнут | Прокси влияет ТОЛЬКО на риск; давать им цену — возврат дефекта `§−38` (нота стоимостью 103.5 оценивалась в 65 по цене `VWOB`) |
| **Цена покупки** | ✅ принят | Ровно то, что уже делается для проксированных бумаг (`priced_at_cost`): позиция остаётся в книге, её вес разбавляет риск, из факторной модели она исключена, P&L = 0 честнее сфабрикованного |
| **Отказ** | ✅ принят как ВТОРОЙ уровень | Решение «строить ли отчёт» принимает C-8 по ДОЛЕ СТОИМОСТИ, а не по факту потери: >10% непокрытой стоимости — BLOCK до списания токена |

Оба уровня нужны вместе: цена покупки сохраняет позицию и делает потерю
видимой, C-8 решает, осмысленна ли книга целиком. Это ровно разделение из
`PHASE_04 §5a.4`: «парсер сообщает про СТРОКИ, чекеры — про ПОСЛЕДСТВИЯ».

### 6.3 Что обязана сделать MP-09

1. Бумага без ряда получает `Current_Price = Purchase_Price` и попадает в
   `priced_at_cost` — независимо от того, проксирована она или нет;
2. её стоимость доезжает до C-8 как **непокрытая**, а не исчезает из знаменателя;
3. строка CoVe называет такие бумаги поимённо.

Спецификация закреплена падающим тестом
`test_uncovered_value_reaches_c8_SPEC_FOR_MP09` (`@expectedFailure`): он
станет зелёным ровно тогда, когда дыра будет закрыта, и не даст «забыть» её при
включении флага.
