## 1. Главный вывод: данные переезд НЕ теряют

Проверено по коду, а не по памяти:

| Что | Чем ключуется | Переживает смену бота? |
|---|---|---|
| Балансы токенов, транзакции | `telegram_id INTEGER PRIMARY KEY` (`db_tokenomics.py:196,204`) | ✅ да |
| Риск-профиль, мандат | `telegram_id` (`db_tokenomics.py:213,258`) | ✅ да |
| Снимки отчётов | `telegram_id` (`db_tokenomics.py:228`) | ✅ да |
| Режим подключения, блокировки, черновик портфеля | `telegram_id PRIMARY KEY` (`db_tokenomics.py:258,286,302`) | ✅ да |
| Ключи брокера (Fernet) | `api_credentials.user_id TEXT` (`finance/security.py:77`) = `str(telegram_id)` (`tg_bot.py:321,327`) | ✅ да |
| Файлы отчётов в GCS | путь по `telegram_id` | ✅ да |

**Причина, по которой это работает:** всё состояние привязано к
`telegram_id` **пользователя**, а не к идентичности бота. Отдельно
проверено: `src/tg_bot.py` и `src/entrypoint.py` **нигде** не вызывают
`get_me()` и не читают `bot.id`/`bot.username` — у бота нет собственного
идентификатора, на который что-то завязано.

> Токен бота — это ключ к очереди `getUpdates`, а не к базе. Поменять его
> для нашего кода примерно то же, что сменить пароль от почтового ящика:
> письма на месте.

**Что переездом теряется — три вещи, все внешние по отношению к коду:**

1. **История переписки со старым ботом.** Она живёт на стороне Telegram и
   не переносится ничем. Отчёты при этом целы (они в GCS и в БД).
2. **Первое сообщение придётся отправить вам.** Бот не может написать
   пользователю первым — нужно один раз нажать `/start` у `@Ombri_bot`.
   При одном пользователе это одно действие; при сотне это была бы
   кампания оповещения.
3. **Кнопка «Применить идею» в уже выпущенных отчётах.** См. §2.

## 2. Единственная реальная потеря: deep-link в старых отчётах

Готовые отчёты — **статический HTML в GCS**. Хэндл бота вшит в них в момент
генерации (`pdf_payload.py:1514`, дефолт `KEN_investment_bot`, env
`BOT_USERNAME` в проде НЕ задан). Значит все ранее выпущенные отчёты
навсегда содержат ссылку `t.me/KEN_investment_bot?start=scn_<n>`.

Что с этим можно сделать честно:

| Вариант | Цена | Оценка |
|---|---|---|
| **Принять** — старые отчёты историчны, новые пойдут с новым хэндлом | 0 | ✅ **рекомендую при одном пользователе** |
| Перегенерировать старые отчёты | прогон движка + списание/обход токеномики | Не оправдано |
| Держать старого бота живым как «редирект» | постоянно работающий второй сервис (см. §4) | ❌ Дороже пользы |

🔴 **Не удаляйте `@KEN_investment_bot` в `@BotFather`.** Освобождённый хэндл
может зарегистрировать кто угодно — и получить чужие входящие по ссылкам из
ваших отчётов. Припаркованный, но не опрашиваемый бот стоит ноль и этой
проблемы не создаёт.

## 3. Рунбук переезда

Код уже умеет всё нужное (`§−101`). Осталось ручное, и оно РАЗДЕЛЕНО:
сначала безопасный мерж, потом одно осознанное переключение.

### Что уже сделано в коде — трогать не надо

```
✅ tg_bot.read_bot_token(): OMBRI_BOT_TOKEN → фолбэк RAMP_BOT_TOKEN с предупреждением
✅ cloudbuild: подстановки _BOT_TOKEN_SECRET и _BOT_USERNAME (пока прежние значения)
✅ переменная в контейнере уже новая: OMBRI_BOT_TOKEN=${_BOT_TOKEN_SECRET}:latest
✅ src/branding.py: OMBRIOS / OMBRI / Ombri_bot / @OMBRI_support_bot
✅ тексты бота, промпты ИИ, бандлы Premium, логгеры ombri.*
✅ тесты: 17 новых, 7 из 7 мутаций пойманы
```

**Мерж и деплой после него безопасны.** Подстановки указывают на прежний
секрет и прежний хэндл, поэтому прод продолжает работать как
`@KEN_investment_bot`, только под новыми текстами и с новым именем переменной
внутри контейнера. Ничего переключать этот деплой не будет.

> 📗 **Пошагово, с командами и проверками — `OPERATOR_SWITCH.md`.**
> Ниже — та же последовательность в сжатом виде.

### 🔴 Шаг A — руками в Google Cloud и Telegram (до переключения)

Это ЕДИНСТВЕННОЕ, что нельзя сделать из репозитория:

```
□ @BotFather → /revoke для @Ombri_bot.
  Токен светился открытым текстом в переписке — считайте его чужим.
  Новый токен НИКУДА не копируйте, кроме следующего шага.
□ Secret Manager → создать секрет OMBRI_BOT_TOKEN со значением нового токена:
    gcloud secrets create OMBRI_BOT_TOKEN --replication-policy=automatic \
      --data-file=- --project=<PROJECT_ID>      # значение подаётся в stdin
□ Дать сервис-аккаунту Cloud Run право читать этот секрет:
    gcloud secrets add-iam-policy-binding OMBRI_BOT_TOKEN \
      --member=serviceAccount:<SA сервиса ramp-bot> \
      --role=roles/secretmanager.secretAccessor --project=<PROJECT_ID>
□ Секрет RAMP_BOT_TOKEN НЕ удалять — он нужен для отката.
```

Бакеты, сервис Cloud Run, Artifact Registry, VPC — **не трогаются**.

### 🔴 Шаг B — переключение: ДВЕ подстановки, одновременно

В триггере Cloud Build (или в `cloudbuild.yaml`) поменять **обе** строки:

```
_BOT_TOKEN_SECRET: OMBRI_BOT_TOKEN     (было RAMP_BOT_TOKEN)
_BOT_USERNAME:     Ombri_bot           (было KEN_investment_bot)
```

Порознь их менять НЕЛЬЗЯ: хэндл вшивается в статический отчёт и становится
кнопкой «Применить идею». Полупереключение ловится тестом, но тест смотрит
файл — значение в ТРИГГЕРЕ он не видит, так что здесь это на вас.

### Шаг C — проверка после деплоя

```
□ В логах: строка старта и ОТСУТСТВИЕ warning про устаревшее имя переменной
□ В Telegram: /start у @Ombri_bot → баланс токенов и мандат на месте
□ Сгенерировать один отчёт → кнопка «Применить идею» ведёт на @Ombri_bot
```

### Шаг D — старый бот

Отдельно закрывать `@KEN_investment_bot` не нужно и нечем: после шага B его
токен **никто не опрашивает**, сообщения уходят в очередь, которую никто не
читает. Бот становится недоступен всем автоматически.

```
□ НЕ удалять бота в @BotFather (см. §2 — освободившийся хэндл заберёт кто угодно)
□ Опционально: @BotFather → /revoke для @KEN_investment_bot,
  чтобы утёкшая копия старого токена стала бесполезной
□ TG_ALLOWED_USERS на проде НЕ ставится: @Ombri_bot остаётся открытым (решение владельца)
```

### Откат

Вернуть **обе** подстановки на прежние значения и передеплоить. Фолбэк в коде
делает откат безопасным в обе стороны: новый код работает и со старым
секретом, потому что читает `RAMP_BOT_TOKEN` вторым.

## 4. «Сделать `@Ken_investment_bot` тестовым» — честный ответ

**Коротко: как постоянный сервис в облаке — нет. Как локальный бот по
требованию — да, и это ничего не стоит.**

### Почему постоянный тестовый сервис дорог

1. **Long-polling бот не умеет масштабироваться в ноль.** В деплое стоит
   `--min-instances=1` и `--no-cpu-throttling` (`cloudbuild.yaml`), и это не
   перестраховка: бот не ждёт входящий HTTP, он сам опрашивает Telegram.
   Значит тестовый сервис — это **постоянно оплачиваемый инстанс**, а не
   «включается, когда тестирую». При 2Gi/1CPU это сопоставимо со стоимостью
   самого прода.

2. **Общее состояние — не экономия, а порча данных.** Если направить
   тестовый сервис на тот же `_STATE_BUCKET`, он станет **вторым писателем**
   в `/mnt/state/tokenomics.db`, `/mnt/state/users_vault.db` и
   `stooq/prices.sqlite`. Инвариант в деплое написан прямым текстом:
   `--max-instances=1  # single instance — SQLite is not multi-writer safe`.
   SQLite поверх gcsfuse не даёт работающих блокировок, и цена нарушения —
   не «медленно», а битые балансы и зашифрованные ключи брокера.

3. **Значит «правильный» тестовый бот требует своей копии всего:** своего
   бакета состояния, своих секретов, своего сервиса. Для проекта с одним
   пользователем это удвоение инфраструктуры ради ручной проверки того, что
   и так проверяют 1861 тест + прогон в зеркале деплой-образа.

### Что вместо этого

| Способ | Стоимость | Что даёт |
|---|---|---|
| **Локальный запуск старого бота по требованию** | 0 ₸ | Полный ручной тест на своей машине: свой `.env`, локальные пути к SQLite, тот же код. Не может задеть прод физически |
| **`TG_ALLOWED_USERS`** | 0 ₸, мгновенно | Закрывает бота от всех, кроме списка id. Есть в коде уже сегодня (`tg_bot.py:3457-3473`): переменная не задана → бот открыт; задана → пускает только своих и один раз вежливо отказывает остальным |
| **Совсем без тестового бота** | 0 ₸ | Тоже честный вариант: главный риск ручного тест-бота — однажды указать его на прод-состояние |

**Рекомендация:** припарковать `@KEN_investment_bot`, не удаляя; поднимать
его локально, когда нужен ручной прогон; на проде держать
`TG_ALLOWED_USERS=148046720`, пока пользователь один. Это даёт всё, ради
чего заводят тестового бота, и не создаёт ни второго счёта, ни второго
писателя в базу.

🔴 При локальном запуске **обязательно** переопределяйте пути:
`TOKENOMICS_DB_PATH`, `VAULT_DB_PATH`, `STOOQ_DB_PATH`, `REPORT_BUCKET_NAME`.
Локальный бот с прод-значениями этих переменных — это тот самый второй
писатель, только запущенный руками.

## 5. Имя меняется «быстро и безболезненно» — как именно (`§−101`)

| Что менять | Где | Сколько правок | Нужен ли редеплой |
|---|---|---|---|
| Название платформы (`OMBRIOS`) | `branding.PROJECT_NAME_DEFAULT` или env `BRAND_PROJECT_NAME` | 1 | да |
| Название бота (`OMBRI`) | `branding.BOT_NAME_DEFAULT` или env `BRAND_BOT_NAME` | 1 | да |
| Хэндл в отчёте | подстановка `_BOT_USERNAME` | 1 (в паре с токеном) | да |
| Имя секрета с токеном | подстановка `_BOT_TOKEN_SECRET` | 1 (в паре с хэндлом) | да |
| Контакт поддержки | `branding.SUPPORT_CONTACT_DEFAULT` или env `SUPPORT_CONTACT` | 1 | да |
| Имя сервиса / бакетов | ⚫ только оператор, и **не нужно** | 0 | — |

Держится это на одном правиле: **имя внешнего объекта живёт в подстановке или
в `branding`, а не литералом в коде.** Гейт на литерал бренда описан в
`README.md §5`; текст в бандле Premium правится в `design/premium_v2/*.jsx` и
пересобирается `build.sh` — руками бандл не трогают.

Единственное оставшееся исключение — фолбэк `'Ombri_bot'` внутри бандла: он
срабатывает, только если `botUsername` вообще не приехал в данные, а
`premium_payload` всегда подставляет значение из `branding`. То есть в проде
этот литерал недостижим и держится ради автономности демо-страниц.
