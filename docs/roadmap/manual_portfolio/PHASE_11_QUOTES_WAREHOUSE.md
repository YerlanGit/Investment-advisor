## 🔴 0. Прочитать до планирования: задача в исходной постановке нарушает I-12

**Постановка владельца:** «загрузка всех котировок с 5-летней историей с Tradernet
на собственную базу; эти данные используются для расчёта риска и доходности и
выдаются клиенту как отчёт; это ещё один слой данных, как Stooq для Manual Portfolio».

**Конфликт.** Витрина, наполненная из Tradernet, **не может обслуживать `manual`**:

> **I-12** (`PHASE_00 §2`, юридический, замечание владельца 2026-07-27):
> «Ни один байт данных Tradernet не участвует в отчёте `manual` — ни цены позиций,
> ни 10 факторных ETF, ни 3 бенчмарка, ни ATR, ни fallback-звено цепочки.»

Юридический статус едет **с данными**, а не с транспортом. Кэш чужих данных не
перестаёт быть чужими данными — БД между Tradernet и пользователем ничего не
меняет, она лишь удлиняет путь. Наивное внедрение открыло бы обход I-12 через
собственное хранилище, причём **молча**: `provider_for_source` проверяет имя
провайдера, а не происхождение строк, которые тот отдаёт.

### 0.1 Разрешение: витрина — это СУБСТРАТ, а не источник

Замысел владельца («ещё один слой данных, как Stooq») структурно верен — меняется
только то, **что именно** считается слоем.

```
БЫЛО в голове:          витрина = ещё один ИСТОЧНИК рядом с Tradernet и Stooq
СТАЛО в архитектуре:    витрина = ХРАНИЛИЩЕ, в котором у каждой строки
                        есть ПРОИСХОЖДЕНИЕ, и оно едет вместе со строкой
```

Одна таблица, две непересекающиеся области:

| `origin` | Наполняется | Обслуживает | Основание |
|---|---|---|---|
| `tradernet` | `freedom-etl`, ключ сервисного счёта | `freedom` | данные брокера — клиенту брокера |
| `stooq` | тот же ETL, публичный CSV | `manual` **и** `freedom` | Stooq публичен (`PHASE_09 §3.2`) |

`WarehouseProvider` параметризуется происхождением, и **`origin` попадает в
`WHERE`**. Смешать источники в одной матрице становится физически невозможно —
не «запрещено правилом», а невыразимо в запросе. Это сильнее любого теста.

### 0.2 Побочный выигрыш: снимается главный операционный риск Фазы 09

`PHASE_09 §3` требует для Stooq циркуит-брейкер (S-8), параллелизм 2 с джиттером
(S-6) и лимит тела 5 МБ (S-3) — потому что «у Stooq нет ни опубликованных лимитов,
ни SLA. Агрессивный параллелизм = бан IP Cloud Run, то есть отключение сервиса
целиком (Т-7)».

Витрина убирает источник этого риска: Stooq опрашивается **плановым ночным job'ом
раз в сутки, батчами, с одного статического IP**, а не в момент построения отчёта
пользователем. Отчёт читает из БД и в Stooq не ходит вовсе.

То же и для Tradernet: Cloudflare-WAF брокера блокирует egress-пул Cloud Run
(`docs/infra/INFRA_NETWORKING.md §1` — «`403 + HTML challenge`… все тикеры
провалились»). Витрина разрывает эту связь на пути отчёта.

### 0.3 Новый инвариант

> **I-14** [нов. 2026-08-09] — **Происхождение едет с данными через хранилище.**
> Каждая строка котировок несёт `origin`; провайдер витрины обязан фильтровать по
> нему, и матрица одного отчёта содержит строки ровно одного `origin`.
> Витрина, наполненная из Tradernet, для `manual` недопустима так же, как сам
> Tradernet.
> **Проверка:** `test_warehouse_origin_in_where` (запрос без `origin` не собирается),
> `test_manual_warehouse_rejects_tradernet_origin`, `test_single_origin_per_matrix`.

I-14 не заменяет I-12 и I-13, а закрывает щель между ними: I-12 говорит про
провайдера, I-13 — про матрицу, и оба молчат про **посредника, который хранит**.

## 3. Изменения схемы

### 3.1 `origin` — происхождение строки

```sql
ALTER TABLE daily_candles
    ADD COLUMN IF NOT EXISTS origin VARCHAR(16) NOT NULL DEFAULT 'tradernet';

ALTER TABLE daily_candles DROP CONSTRAINT daily_candles_pkey;
ALTER TABLE daily_candles ADD PRIMARY KEY (ticker, trade_date, origin);
```

🔴 **`origin` входит в первичный ключ.** Иначе одна бумага не может лежать в
витрине дважды — а именно это и нужно: `AAPL.US` от Tradernet и `AAPL.US` от Stooq
— **разные ряды разных конвенций**, и схлопывать их в одну строку значит потерять
ровно то различие, ради которого вводится I-14.

Дефолт `'tradernet'` делает миграцию совместимой с уже налитыми данными: строки,
записанные до этой фазы, происходят из Tradernet по построению.

`sync_status` и `tracked_tickers` получают `origin` тем же способом — курсор у
каждого источника свой, и универсумы не обязаны совпадать (KZ-бумаг на Stooq нет,
`PHASE_08 §2.5`).

### 3.2 `corporate_actions` — события, а не пересчитанные цены

```sql
CREATE TABLE IF NOT EXISTS corporate_actions (
    ticker       VARCHAR(20)  NOT NULL,
    action_date  DATE         NOT NULL,
    action_type  VARCHAR(16)  NOT NULL,   -- 'split' | 'dividend'
    ratio        NUMERIC(12,6),           -- 10 = 1 акция → 10 акций
    amount       NUMERIC(12,4),
    source       VARCHAR(32)  NOT NULL,   -- 'known_splits' | 'heuristic' | 'manual'
    PRIMARY KEY (ticker, action_date, action_type)
);
```

**Почему события, а не скорректированные цены.** Корректировать на записи —
значит переписывать всю историю бумаги задним числом при каждом новом сплите.
Хранение сырого ряда + событий делает запись append-only и аудируемой: сплит — это
одна вставка, а не `UPDATE` на 1 260 строк.

Колонка `source` обязательна: событие из `KNOWN_SPLITS` и событие, найденное
эвристикой, — разного качества, и без разделения их нельзя пересмотреть, когда
эвристика ошиблась.

### 3.3 Конвенция: хранится RAW, применяется на чтении

| Слой | Конвенция | Кто отвечает |
|---|---|---|
| `daily_candles` | **RAW** — как отдал источник | `freedom-etl` |
| `WarehouseProvider.fetch` → выход | **SPLIT_ADJUSTED** | `src/`, общая функция |

Это прямо поддержано **I-6**: «`KNOWN_SPLITS` и `_detect_and_adjust_splits`
остаются включёнными для всех провайдеров; они идемпотентны». Идемпотентность и
позволяет применять их на чтении, не боясь двойной корректировки.

🔴 Корректировка — это **число**, а числа считаются только в `finance/*`
(корневой `CLAUDE.md`). Поэтому она не переезжает в ETL: `freedom-etl` хранит и
отдаёт, `src/` считает.

## 4. Сторона `src/` — два новых модуля, движок не меняется

### 4.1 `src/services/quotes_store.py` (L1, read-only)

Тонкий синхронный клиент. **Ничего не решает** — весь SQL заперт здесь, как в
`db/connection.py` у ETL.

```python
def fetch_prices(tickers, *, days, origin) -> tuple[pd.DataFrame, dict[str, str]]
def coverage(tickers, *, days, origin) -> dict[str, int]     # тикер → наблюдений
def corporate_actions(tickers) -> dict[str, list]
```

🔴 `origin` — **обязательный именованный параметр без дефолта**. Дефолт означал бы,
что забывший его вызов молча получит какие-то данные; здесь он обязан не собраться.

> **Почему синхронный, а не asyncpg.** `get_market_data` — синхронный код внутри
> `analyze_all`, который сам крутится в `run_in_executor`. Тащить туда event loop
> значит городить мост ради драйвера. `psycopg` 3 в sync-режиме честнее.

### 4.2 `WarehouseProvider` в `finance/price_providers.py`

```python
class WarehouseProvider:
    """Витрина. Происхождение фиксируется в КОНСТРУКТОРЕ и уезжает в WHERE."""
    convention = PriceConvention.SPLIT_ADJUSTED   # ПОСЛЕ применения корректировки
    max_parallelism = 1                           # один SQL на весь батч

    def __init__(self, origin: str) -> None:
        if origin not in _WAREHOUSE_ORIGINS:      # {'tradernet', 'stooq'}
            raise ProviderUnavailable(...)        # fail-CLOSED, как A-3
        self.origin = origin
        self.name = f"warehouse:{origin}"
```

`name` несёт происхождение (`warehouse:stooq`) — иначе CoVe и
`ProviderResult.source` не смогут его показать, а `single_source()` признал бы
две разные витрины одним источником.

### 4.3 Реестр и юридическая граница

```python
_REGISTRY = {
    "tradernet":         TradernetProvider,
    "demo":              DemoProvider,
    "warehouse:stooq":   lambda: WarehouseProvider("stooq"),      # manual + freedom
    "warehouse:tradernet": lambda: WarehouseProvider("tradernet"),# ТОЛЬКО freedom
}

_MANUAL_FORBIDDEN = frozenset({"tradernet", "warehouse:tradernet"})
```

🔴 **`warehouse:tradernet` обязан быть в `_MANUAL_FORBIDDEN`.** Это и есть I-14 в
коде. Тест обязан падать при удалении имени из множества — иначе правило
существует только в этом документе.

Ничего. `get_market_data` (`risk_engine.py:973`) уже работает через

## 5. Гейт покрытия и failover (I-13)

Соблазн «чего нет в витрине — доберём у источника» **запрещён**: `PHASE_00 §3a.1a`
отменил по-тикерный failover замечанием владельца.

```
coverage = quotes_store.coverage(all_req, days=period_days, origin=origin)
витрина принимается, если:
    все запрошенные тикеры присутствуют
  И min(наблюдений) ≥ MIN_OBS_WAREHOUSE
  И последний close не старше N ТОРГОВЫХ дней
иначе → ВЕСЬ отчёт уходит на живой провайдер, факт → в CoVe
```

Для `freedom` резерв — `TradernetProvider`. Для `manual` резерв — **живой
`StooqProvider` Фазы 09**, и только он; отсутствие Фазы 09 означает, что у
ручного портфеля резерва нет вовсе, и гейт обязан блокировать отчёт честным
отказом без списания токена (как сегодня делает `ProviderUnavailable`).

🔴 Гейт считается **до** расчёта и **до** списания токена — как pre-flight
ручного портфеля (`AUDIT §−71`).

### 5.1 Порог свежести — в торговых днях

`TRADERNET_FRESH_CAL_DAYS = 5` (`data_lineage.py:54`, применяется `:111`) — в
календарных днях. Витрина по построению отдаёт T-1, и после длинных выходных
(Рождество, День независимости РК) последний close окажется 4–5 дней назад:
отчёты начнут массово показывать `stale` там, где данные корректны.

Порог переводится в торговые дни. Это не косметика: бейдж свежести — часть
продукта, а бейдж, который врёт в обе стороны, хуже отсутствующего.

## 7. Первичный бэкфилл (5 лет)

Отдельный режим, а не побочный эффект первого планового прогона.

```bash
python main.py --backfill --origin tradernet --days 1825
```

| Параметр | Значение | Обоснование |
|---|---|---|
| Окно | 1825 кал. дней ≈ 1260 торговых | ровно `HISTORY_LOOKBACK_DAYS` (`risk_engine.py:1000`) — витрина обязана покрывать окно движка, иначе гейт §5 не пропустит её никогда |
| Объём | ~500 тикеров × 1260 ≈ **630 тыс. строк** | на порядки ниже, чем нужно TimescaleDB |
| Время | ~10 батчей/мин × 50 → **≈20 мин на 500 бумаг** | пауза 2 с между батчами доминирует |
| Возобновляемость | по `sync_status`, прерывание безопасно | курсор двигается только после записи |

🔴 **Бэкфилл идёт ОДИН раз и вручную.** Автозапуск при пустой БД отвергнут:
падение и пересоздание тома превратили бы аварию в 20-минутный шторм запросов к
брокеру, неотличимый от злоупотребления.

## 9. Инфраструктура

| Компонент | Решение | Обоснование |
|---|---|---|
| БД | **Cloud SQL PostgreSQL 16**, без TimescaleDB | 630 тыс. строк — обычная таблица с btree; TimescaleDB окупается на 10⁸+. Расширения на Cloud SQL нет, и оно не нужно |
| Сеть | тот же Serverless VPC + Cloud NAT | статический egress уже настроен (`scripts/setup_static_egress.sh`) — он же решает WAF-блок |
| ETL | **Cloud Run Job** + Cloud Scheduler | работа конечная; платить за простой сервиса незачем |
| Доступ бота | роль `ramp_reader`, только `SELECT` | бот физически не может испортить витрину — дешевле любого код-ревью |
| Секреты | Secret Manager | тот же паттерн, что `cloudbuild.yaml:107` |

🔴 `--set-env-vars` **заменяет весь набор** переменных Cloud Run
(`cloudbuild.yaml:121` — это уже стоило инцидента). `QUOTES_DB_URL` дописывается в
существующую строку, а не отдельным флагом.

`--max-instances=1` (`cloudbuild.yaml:94`) **остаётся**: он привязан к SQLite
токеномики, а не к ценам.

Деградация без TimescaleDB проверена на живом PostgreSQL 16: `apply_schema`
возвращает `False`, пишет предупреждение, данные и запросы работают. Решение
обратимо — `create_hypertable(..., migrate_data => TRUE)` уже в DDL.

## 12. Что осознанно НЕ делается

| Не делаем | Почему |
|---|---|
| Дивидендная корректировка (`TOTAL_RETURN`) | движок нигде её не ждёт; смена конвенции меняет ВСЕ доходности — отдельный проект с пересмотром эталонов |
| Перенос `KNOWN_SPLITS` в ETL | нарушит SSOT; в БД едут её **данные**, таблица остаётся в `src/` |
| Отказ от `/tmp`-кэша `history.py` | он обслуживает живой путь, который остаётся резервом (I-13) |
| Снятие `--max-instances=1` | ограничение от SQLite токеномики, к ценам отношения не имеет |
| Автобэкфилл при пустой БД | авария превратилась бы в шторм запросов к брокеру |
| Intraday | движок оперирует дневными свечами; схема заточена под `trade_date` |
| Разрешение `manual` на `warehouse:tradernet` «для клиентов брокера» | отвергнуто в `PHASE_00 §3a.1` по трём причинам; витрина ничего в них не меняет |
