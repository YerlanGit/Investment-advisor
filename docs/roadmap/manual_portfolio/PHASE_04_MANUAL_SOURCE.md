## 1. Цель

Модуль `src/finance/manual_portfolio.py`, превращающий текст пользователя
в **тот же самый** `DataFrame`, который отдаёт `FreedomConnector` — так, чтобы
`analyze_all()` отработал на ручном портфеле без единой правки движка (I-2).

Модуль **не импортирует `tg_bot`** и ничего не знает про Telegram: на входе строка,
на выходе `DataFrame` + отчёт о разборе. Это делает его тестируемым офлайн
и переиспользуемым в Фазе 7 (CSV/XLSX).

## 2. Целевой контракт DataFrame

Восстановлен по `broker_api.FreedomConnector._to_dataframe` (строки 287-357) — воспроизводить
надо ровно его, включая порядок колонок.

```python
columns = ["Ticker", "Quantity", "Purchase_Price", "Broker_Current_Price",
           "Asset_Type", "Raw_Ticker"]
```

Рисковая позиция:

```python
{"Ticker": "AAPL", "Quantity": 10.0, "Purchase_Price": 150.50,
 "Broker_Current_Price": None,          # цену даст провайдер — приоритет (2)
 "Asset_Type": _classify_instrument("AAPL"),
 "Raw_Ticker": "AAPL.US"}                # как ввёл пользователь
```

Денежная строка — дословно как у брокера (`broker_api.py:343-350`):

```python
{"Ticker": "USD", "Quantity": 5000.0, "Purchase_Price": 1.0,
 "Broker_Current_Price": 1.0, "Asset_Type": "Кэш", "Raw_Ticker": "USD"}
```

**Три детали, которые легко упустить:**

1. **`Ticker` без биржевого суффикса.** Брокерский путь прогоняет тикер через
   `_strip_exchange_suffix` (`AAPL.US` → `AAPL`, строка 297), а полный тикер кладёт
   в `Raw_Ticker`. Ручной ввод обязан делать то же: иначе `resolve_tickers` получит
   `AAPL.US` вместо `AAPL` и пойдёт другой веткой (`'.' in t_str` → passthrough,
   строка 711 — вместо ветки 7 `f"{t}.US"`). Результат тот же, но полагаться на это нельзя:
   для `BRK.B` ветки расходятся.
2. **`Broker_Current_Price = None` у рисковых позиций.** Ручной ввод не знает рыночной
   цены. `None` заставляет `analyze_all` взять цену из ценовой матрицы (приоритет 2,
   строка 1686) — правильное поведение. Подставлять сюда `Purchase_Price` **нельзя**:
   это включит ветку `broker_priced_only` (1689-1692), позиция вылетит из факторной модели,
   а PnL станет тождественно нулевым.
3. **`Asset_Class` / `Asset_Class_Label` не нужны.** Брокерский путь их формирует
   (строки 329-330), но конструктор `pd.DataFrame(rows, columns=[...])` их **отбрасывает** —
   в списке колонок их нет. Ручной ввод их не создаёт: паритет сохраняется.

**Маркеры `df.attrs`.** Ручной портфель — реальный, поэтому **ни один** из
`_ramp_is_mock` / `_ramp_is_fallback` не ставится (иначе сработает гейт
`analyze_all:1625-1636` и `tg_bot:2117-2134`). Ставится один новый:
`df.attrs["_ramp_source"] = "manual"` — по образцу существующего `"demo"` (`broker_api.py:209`).

## 3. Текстовый формат

Строго по §3.2 задания. Одна позиция — одна строка, разделитель — пробел, табуляция,
запятая или точка с запятой; единообразие внутри строки не требуется.

```
ТИКЕР  КОЛИЧЕСТВО  ЦЕНА_ПОКУПКИ
CASH:USD  5000                      # кэш — два поля, цена = 1.0 по определению
```

| Правило | Поведение |
|---|---|
| Строки с `#` и пустые | Игнорируются |
| Регистр тикера | Приводится к верхнему |
| Десятичный разделитель | Точка и запятая равнозначны: `150,50` = `150.50` |
| Разделители разрядов | Пробел и `_` внутри числа удаляются: `2 500 000` = `2500000` |
| `CASH:XXX` | → `Ticker=XXX`, `Purchase_Price=1.0`, `Asset_Type="Кэш"` |
| Голая валюта из `NON_RISK_ASSETS` (`USD 5000`) | Принимается как кэш, эквивалент `CASH:USD` |
| Цена у кэша указана и ≠ 1.0 | Ошибка строки с пояснением |
| Дубликат тикера | Суммируются; цена покупки — средневзвешенная по количеству; результат склейки показывается пользователю |
| Отрицательные и нулевые количество/цена | Ошибка строки с номером |
| Тикер не прошёл `resolve_tickers()` или не дал истории | Строка помечается и **исключается**, не подставляется |

**Короткие продажи не поддерживаются.** Движок, стресс-тесты и Black-Litterman рассчитаны
на длинные позиции; отрицательное количество даёт отрицательный вес, а `composite_risk_score`
и Euler-декомпозиция на таких весах молча выдают бессмыслицу. Явный отказ с пояснением.

### 3.1 Неоднозначности формата, не покрытые заданием

Разобрать явно, иначе они станут дефектами:

| Случай | Решение |
|---|---|
| Два поля, но тикер **не** валюта (`AAPL 10`) | Ошибка строки: «не указана цена покупки». Не догадываться |
| `CASH 5000` — `CASH` есть в `NON_RISK_ASSETS`, но это не валюта | Ошибка: «укажите валюту, например `CASH:USD`». Псевдо-тикер `CASH` от брокера не приходит никогда (`acc` даёт коды валют) |
| Четыре и более полей | Ошибка строки с указанием, сколько полей ожидалось |
| Разделитель разрядов **и** десятичная запятая: `2 500,50` | Пробелы убираются, запятая → точка → `2500.50`. Порядок операций важен |
| Запятая как разделитель полей **и** как десятичная: `AAPL,10,150,50` | **Неразрешимо.** Ошибка строки с требованием использовать пробел или `;` при десятичной запятой. Угадывать нельзя — цена «150.50» и цена «150» с лишним полем неразличимы |
| Дубликат кэша в одной валюте (`CASH:USD` дважды) | Суммируется, как и тикеры; средневзвешенная цена не считается — она тождественно 1.0 |
| Дубликаты с разной формой (`AAPL` и `AAPL.US`) | Склеиваются **после** нормализации `Ticker`, то есть считаются одной позицией |

### 3.2 Валидация тикера — два разных слоя (ловушка Т-2)

Задание в одном месте запрещает свою регулярку (Т-2), в другом требует whitelist (S-1).
Противоречия нет — это разные слои, и путать их нельзя:

- **Слой ввода** (эта фаза): проверяется только то, что строка непуста, не длиннее
  32 символов и не содержит управляющих символов/переводов строки. Авторитет
  распознавания — `resolve_tickers()` со всеми семью его правилами (кэш, облигации→прокси,
  AIX→прокси, `TICKER_MAP`, крипто, passthrough, `.US`). Своей биржевой логики здесь нет (Т-4).
- **Слой провайдера** (Фаза 9): whitelist S-1 `^[a-z0-9][a-z0-9._-]{0,19}$` — **после**
  приведения к нижнему регистру и **до** сборки URL, далее `urllib.parse.quote`.

Тикеры `AAPL.US`, `BTC-USD`, `FFSPC0824.AIX` обязаны проходить слой ввода без потерь.

## 4. Разбор → отчёт, а не исключение

```python
@dataclass
class ParsedPosition:
    raw_line:   str
    line_no:    int
    ticker:     str
    quantity:   float
    price:      float
    is_cash:    bool
    currency:   str | None

@dataclass
class ParseReport:
    positions: list[ParsedPosition]
    errors:    list[tuple[int, str]]   # (номер строки, человеческая причина)
    merged:    list[tuple[str, int]]   # склеенные дубликаты: (тикер, сколько строк)
    def to_dataframe(self) -> pd.DataFrame: ...
```

Парсер **никогда не бросает** на пользовательском вводе: любая проблема — запись
в `errors` с номером строки. Экран подтверждения (Фаза 5) показывает и принятое,
и отвергнутое — пользователь видит, что именно потерялось.

## 5. Кэш в валюте ≠ базовой — самый тяжёлый пункт фазы

### 5.1 Дефект

Найдено при разборе (`README.md §3`, F-2), заданием не обнаружено.
`analyze_all` пиннит цену кэша безусловно:

```python
# investment_logic.py:1681-1683
if orig_str in self.engine.NON_RISK_ASSETS:
    current_prices[orig] = 1.0
    continue
```

FX применяется к **матрице цен** (`_apply_fx_conversion`, строка 774), а строки кэша
до неё не доходят — они не тикеры. Значит `CASH:KZT 2500000` из примера §3.2 задания
входит в портфель как **2 500 000 у.е.**: при книге акций на $10 000 тенговый остаток
(≈ $4 800) получает вес 99.6% вместо ≈32%, и вместе с ним уезжают TRC, CVaR, беты,
Black-Litterman и композитный риск-индекс. Ни одного визуального признака ошибки.

Тот же путь проходит тенговый остаток с брокерского счёта (`broker_api.py:336-351`),
то есть **дефект существует и без этой ветки** — на freedom-пути, у любого KZ-клиента.

### 5.2 Решение в границах I-2

`analyze_all` заморожен, поэтому конвертация выполняется **до** него, в слое `manual`:

```
CASH:KZT 2 500 000
  → курс KZT→USD из services.fx_feed (последнее наблюдение DEXKZUS)
  → {"Ticker": "USD", "Quantity": 4 807.69, "Purchase_Price": 1.0, ...}
  → в CoVe: «Кэш KZT 2 500 000 → USD 4 807.69 по курсу 520.0 на 2026-07-24»
```

Правила:

- базовая валюта — `ReportingCurrency.from_env()`, та же, что у движка
  (`investment_logic.py:478-483`), рассинхрон недопустим;
- курс берётся тем же `services.fx_feed`, что и для цен, — один источник, один лаг;
- **строки кэша в разных валютах после конвертации схлопываются в одну** строку
  базовой валюты (иначе в портфеле окажутся `USD` и `USD` дважды);
- курс и дата наблюдения обязательно уходят в CoVe: конвертация не должна быть невидимой.

### 5.3 Валюта без курса

`fx_feed` регистрирует `USD↔KZT` (`DEXKZUS`) и `GBP↔USD` (`DEXUSUK`) — строки 54-63.
**Задание утверждает, что поддерживается только USD↔KZT (ошибка E-3), но вывод
от этого не меняется:** для `EUR` и `RUB`, которые есть в `NON_RISK_ASSETS`, курса нет.

Поведение — по §3.5 задания, без послаблений:

1. На экране подтверждения — явное предупреждение с названием валюты;
2. Пользователь выбирает: исключить позицию или продолжить без неё;
3. В обоих случаях — строка DEGRADE (C-11) в CoVe;
4. **Молчаливое `1.0` не остаётся ни на одном пути** (Т-5).

Расширять `FRED_FX_SERIES` парами EUR/RUB — вне объёма фазы: это отдельное решение
про источник и его надёжность, а не часть ручного ввода.

### 5.4 Что делать с freedom-путём

Дефект F-2 существует независимо. Варианты:

- **(a)** починить в этой же ветке — перенести конвертацию кэша в общий слой
  до `analyze_all` для обоих источников. Технически чисто, но расширяет объём
  и требует пересчёта снапшотов I-5 (числа freedom-отчётов с тенговым кэшем **изменятся** —
  в правильную сторону, но изменятся);
- **(b)** отдельным PR после ветки.

**Рекомендация — (b)**, и строка в `docs/audit/AUDIT.md` **немедленно**, в этой фазе:
иначе находка растворится. Решение за владельцем продукта (пункт ★ в `README.md §7`).

## 5a. Предвыполненный анализ фазы (2026-07-29)

Проверка кода после завершённых Фаз 1–3. Четыре уточнения к плану.

### 5a.1 Контракт DataFrame изменился — витрина уже показала эталон

`finance/demo_portfolio.build_demo_portfolio` (раунд 31) строит ровно тот фрейм,
который нужен ручному вводу: те же шесть колонок, `Broker_Current_Price=None`
у рисковых, `1.0` у денежных, `Asset_Type` из `_classify_instrument`.
**Это готовая референс-реализация** — Фаза 4 повторяет её структуру, отличаясь
только источником строк (текст пользователя вместо константы).

Практический вывод: контракт можно не выводить заново из `broker_api`, а
сверять тестом с витриной — расхождение сразу видно.

### 5a.2 🔴 Маржинальный заём: отрицательное количество ≠ короткая продажа

План запрещает отрицательные количества («короткие продажи не поддерживаются»).
Аудит живого отчёта показал случай, который под этот запрет **не подпадает**:
денежная строка `USD` с ОТРИЦАТЕЛЬНЫМ остатком — это маржинальный заём, и
портфели с ним считаются корректно (Σ весов = 1.0, плечо 1.07×).

Значит правило парсера надо расщепить:

| Ввод | Решение |
|---|---|
| `AAPL -10 150.50` | ошибка строки — короткая продажа не поддерживается |
| `CASH:USD -5000` | **принимается** как маржинальный заём |

Без этого расщепления ручной ввод не сможет описать книгу, которую брокерский
путь обрабатывает штатно, — и I-1 («manual структурно идентичен freedom»)
нарушится на первом же реальном портфеле с плечом.

### 5a.3 Конвертация кэша: FX-провайдер уже доступен движку

`MAC3RiskEngine.__init__` авто-подключает `services.fx_feed.default_fx_provider()`.
Слою `manual` не нужен свой FX-слой — достаточно взять тот же провайдер, чтобы
курс и его дата совпали с тем, что отчёт покажет в CoVe. Разные курсы в
конвертации кэша и в матрице цен дали бы расхождение, которое ничем себя не
проявит (ровно класс дефекта F-2).

### 5a.4 Чекеры Фазы 3 закрывают часть работы парсера

`check_portfolio_sufficiency` уже умеет то, что план предписывал парсеру:
C-7 ловит «меньше двух рисковых», C-8 — потерю стоимости на нераспознанных
тикерах, C-11 — валюты без курса. Парсер **не должен это дублировать**: его
задача — разобрать текст и честно перечислить, что отброшено, а решение
«строить ли отчёт» принимают чекеры на общем основании.

Разделение важно и по UX: парсер сообщает про СТРОКИ («строка 4: BADTICKER»),
чекеры — про ПОСЛЕДСТВИЯ («54% стоимости портфеля не покрыто»).

### 5a.5 Что перепроверено и осталось верным

- `resolve_tickers` после фикса `BTC-USD` (раунд 31) корректно обрабатывает
  крипто-форму с суффиксом — ловушка Т-2 закрыта, своя регулярка не нужна;
- `_effective_cost("deep", "manual") == 2` — правки не требует (I-4);
- ветка `manual` в `_resolve_portfolio_source` обязана стоять ДО проверки vault
  (F-4) — не сделано, входит в объём Фазы 5.

## 5b. Разбор внешнего ТЗ на Фазу 4 (2026-07-29)

Поступило подробное ТЗ на реализацию (PERSONA/INSTRUCTIONS/CONTEXT/OUTPUT).
Направление верное и совпадает с планом; ниже — только расхождения и находки,
которые надо снять ДО кодирования. Отсортировано по severity.

### 🔴 A. Блокеры

**A-1. Флоу физически не сможет построить отчёт до Фазы 9.**
ТЗ (Блок 3, Commit 3) предписывает «передай `df` в `analyze_all()`». Но
`provider_for_source("manual")` сегодня поднимает `ProviderUnavailable`:
данные Tradernet для ручного портфеля запрещены (I-12), а `StooqProvider`
появится только в Фазе 9. То есть кнопка «🚀 Рассчитать» отработает до первого
обращения за ценами и честно упадёт.

*Это не повод не делать Фазу 4* — она разрабатывается и тестируется на офлайн-
фикстурах. Но `MANUAL_PORTFOLIO_ENABLED` в проде остаётся `off`, и ТЗ должно это
зафиксировать, иначе фаза «сдана», а фича не работает.

**A-2. Цена покупки в локальной валюте ломает P&L — а именно она в примере ТЗ.**
ТЗ вводит FX-guardrail только для КЭША. Но `_apply_fx_conversion` конвертирует
**матрицу цен**, а `Purchase_Price` приходит из пользовательского фрейма и
используется сырым (`investment_logic.py:1753`). На примере из самого ТЗ —
`KMGZ.KZ 100 12000` (12 000 ₸):

```
Current_Price  = сконвертирована в USD      ≈ $25
Purchase_Price = 12000, трактуется как USD
Total_Cost     = 100 × 12000  = $1 200 000
Current_Value  = 100 × 25     = $2 500
Return_Pct     = −99.8%
```

Отчёт покажет катастрофический убыток на ровном месте. Дефект **шире ручного
ввода**: брокер тоже отдаёт `price_a` в валюте инструмента, значит freedom-путь
с KASE-позициями страдает так же — это F-2 в новой проекции, и его надо
завести отдельной строкой в `AUDIT.md`.

Решение для Фазы 4: конвертировать `Purchase_Price` тем же курсом и на ту же
дату, что и кэш, либо (честнее) спрашивать валюту цены явно и показывать её на
экране подтверждения. Молча трактовать как USD — недопустимо.

### 🟡 B. Архитектурные расхождения

**B-1. Локальный `TICKER_MAP` в парсере — прямое попадание в ловушку Т-4.**
`MAC3RiskEngine.TICKER_MAP` уже содержит `KASPI/KSPI → KSPI.KZ`,
`HALYK/HSBK → HSBK.IL`, `KAZATOMPROM → KAP.IL`, `KAZAKHTELECOM → KZTK.KZ`.
Второй словарь в слое ввода = два источника правды, которые разъедутся:
пользователь, написавший «каспи», и брокер, приславший `KSPI`, попадут в разные
ветки. Синонимы надо **дополнить в существующий `TICKER_MAP`**, а парсер обязан
звать `resolve_tickers()` — это и есть авторитет распознавания (Т-2).

Побочно: `KEGOC` и `KMG` в движке отсутствуют — их добавление полезно, но
именно в движок.

**B-2. Pre-flight check блокирует интерактивный хендлер.**
«Проверь наличие ценовой истории» до экрана подтверждения — это сетевой поход
за ~20 рядами внутри обработчика кнопки. aiogram long-poll этого не любит, а
пользователь видит зависший интерфейс. Плюс работа дублируется: `analyze_all`
пойдёт за теми же рядами снова.

Что делать: (а) выполнять проверку в `run_in_executor` с промежуточным
сообщением «Проверяю тикеры…»; (б) опереться на кэш Фазы 1 — pre-flight
прогревает его, и последующий анализ попадает в него же (TTL 1 ч).

**B-3. `MemoryStorage` теряет ввод при рестарте, Redis — не-цель.**
CONTEXT предлагает «MemoryStorage/RedisStorage». Redis прямо назван не-целью в
исходном задании; `MemoryStorage` теряет 20-позиционный ввод при любом
передеплое Cloud Run. Ответ уже есть в плане — черновик в существующей SQLite
(`PHASE_05 §5`), без новой инфраструктуры.

**B-4. Экран подтверждения без кнопки «Отмена».**
ТЗ даёт ровно две кнопки. Пользователь, увидевший, что распозналось не то,
остаётся заперт в FSM. Требуется третья кнопка + `try/finally` на освобождение
single-flight слота во всех ветках (ловушка Т-9).

### 🟢 C. Дублирование уже сделанного

## 5c. Решение по A-2: валюта сделки (решения владельца 2026-07-29)

Приняты: A-1 (сдача с флагом `off` до Фазы 9) · B-1 (единый словарь) ·
A-2 (валюта сделки в шаблоне, обратная конвертация в Action Plan, курс — текущий).
Ниже — проработка A-2 до уровня, на котором её можно кодировать.

### 5c.1 Валюту НЕ надо спрашивать в общем случае — движок её уже знает

`finance.currency.infer_asset_currency` выводит валюту из тикера, и это уже
работает для матрицы цен:

| Тикер | Валюта | Откуда |
|---|---|---|
| `AAPL.US` | USD | `_EXCHANGE_TO_CURRENCY['US']` |
| `KSPI.KZ`, `KMGZ.KZ` | **KZT** | `_EXCHANGE_TO_CURRENCY['KZ']` |
| `KAP.IL`, `HSBK.IL` | USD | `_TICKER_CURRENCY_OVERRIDE` (GDR торгуются в долларах) |
| `FFSPC….AIX` | USD | `_EXCHANGE_TO_CURRENCY['AIX']` |

Поэтому шаблон остаётся коротким, а валюта — **необязательным четвёртым полем**:

```
AAPL       10    150.50           # USD выводится из .US
KMGZ.KZ    100   12000            # KZT выводится из .KZ — вводить не нужно
KMGZ.KZ    100   25      USD      # ЯВНОЕ переопределение, если куплено за доллары
CASH:USD   5000
```

Так лучше не только по UX: пользователь, написавший «USD» у казахстанской бумаги
по невнимательности, создал бы ошибку конвертации, которой при выводе из тикера
просто нет. Явное поле остаётся для реального случая — покупка через
валютный счёт по кросс-курсу.

### 5c.2 Каким именно курсом конвертировать

**Не свежим спотом, а тем же курсом, которым сконвертирована последняя строка
матрицы цен.** Он уже доступен: `convert_price_matrix` возвращает
`FxConversion.last_value` на каждую пару, а движок сохраняет их в
`_last_fx_records`. Матрица использует лагированный на день курс
(`lag_one_day=True`, защита от look-ahead) — если взять «сегодняшний спот»,
он разойдётся с матрицей, и в P&L протечёт паразитный FX-остаток.

### 5c.3 Что при этом становится с доходностью — главное следствие

Если обе стороны конвертированы ОДНИМ курсом `r`:

```
Return_Pct = (P_now/r − P_buy/r) / (P_buy/r) = (P_now − P_buy) / P_buy
```

Курс сокращается тождественно. То есть `Return_Pct` для валютной позиции
становится **доходностью в валюте инструмента**, а не доходностью
долларового инвестора: движение тенге с момента покупки в неё не входит.

Это ровно то, что владелец и просил («текущий курс, изменение курса не
учитываем»), но это **конвенция, а не приближение** — и её надо назвать в отчёте,
иначе читатель решит, что видит свою долларовую доходность.

Что при этом СОХРАНЯЕТСЯ корректным (проверено по коду):

| Величина | Корректность |
|---|---|
| `Current_Value`, `Total_Cost` | ✅ в базовой валюте по текущему курсу |
| Веса позиций (`Current_Value/total`) | ✅ не задеты — единый курс в числителе и знаменателе |
| Вся риск-математика | ✅ считается по матрице цен, `Purchase_Price` в неё не входит |
| Стоимость портфеля, мандатные доли | ✅ |
| `Return_Pct` валютной позиции | ⚠️ доходность в валюте инструмента (FX-нейтральная) |

**Скрытая ошибка, которую надо зафиксировать честно:** портфельная доходность
`port_return = Return_Pct @ weights` (`investment_logic.py:2059`) при таком
подходе складывает доходности, измеренные в РАЗНЫХ валютах. Для книги, где
валютных позиций несколько процентов, искажение пренебрежимо; для книги 50/50
USD/KZT — уже нет. Требуется строка в CoVe с долей не-базовых позиций,
чтобы читатель видел масштаб допущения.

### 5c.4 Обратная конвертация в Action Plan — только отображение

Уровни (`price`, `target`, `stop`) считаются от цены из сконвертированной
матрицы, то есть в базовой валюте. Показывать владельцу KASE-бумаги «$25»,
когда он выставляет заявку в тенге, — бесполезно.

Правильная развязка: **движок отдаёт оба значения**, отчёт выбирает.
`action_plan.AssetActionRow` дополняется полями `currency`, `price_local`,
`target_local`, `stop_local`; `pdf_payload` только форматирует. Так инвариант
«числа считаются в `finance/`, слой отчёта не вычисляет» не нарушается —
иначе обратная конвертация расползётся по шаблонам.

### 5c.5 🔴 Скрытая ошибка: GBX (пенсы) — риск ×100

`_EXCHANGE_TO_CURRENCY` даёт `IL/LSE/L → GBX`, и `convert_price_matrix` делит
цену на 100 (пенсы → фунты) перед кросс-курсом. Для ручного ввода это ловушка:
цену лондонской бумаги пользователь может ввести и в пенсах, и в фунтах, а
ошибка в 100 раз не даст ни одного признака.

Казахстанские кейсы безопасны — `KAP.IL`/`HSBK.IL` переопределены в USD. Но
произвольный `.L`-тикер опасен. Решение: для инструментов, у которых выведенная
валюта — `GBX`, **требовать явное указание валюты** и не угадывать.

### 5c.6 Итог по A-2 (что кодировать)

1. Парсер принимает необязательное 4-е поле — код валюты; по умолчанию
   `infer_asset_currency(resolved_ticker)`;
2. `GBX` → валюта обязательна, иначе ошибка строки;
3. конвертация `Purchase_Price` **и** кэша одним курсом — `FxConversion.last_value`
   из тех же `_last_fx_records`, что у матрицы;
4. на экране подтверждения: исходная цена, валюта, курс, результат — четыре
   числа, чтобы конвертация была видимой;
5. `action_plan` отдаёт `*_local` + `currency`; отчёт показывает уровни в валюте
   торговли, оставляя базовую в скобках;
6. строка CoVe: «доходность валютных позиций измерена в валюте инструмента;
   доля таких позиций N%».

## 5d. Проверка Фазы 4 на скрытые ошибки (перед разработкой)

Помимо A-2 (§5c) и уже разобранного в §5a/§5b — четыре находки.

**H-1. `resolve_tickers` не сообщает, что подменил бумагу прокси. — ✅ ЗАКРЫТО
2026-07-29** (полный разбор: `AUDIT.md §−38`, математика: `MATH_ENGINE.md §2.3a`).

Подмена оказалась **заложенной логикой**: у неликвидной бумаги нет пригодного
ценового ряда, поэтому в фактор-модель берётся ликвидный индекс. Дефектным было
то, ЧТО подставлялось и КАК далеко подмена расходилась. Сделано:

- прокси переведены на EM (`VWOB.US` для AIX-нот и KZ-долга, `VWO.US` для
  неликвидных EM-акций) — `LQD.US`/`BIL.US` занижали риск KZ-бумаг;
- **прокси больше не даёт цену позиции**: нота, стоящая у брокера 103.5,
  оценивалась в 65 (цена `VWOB`) → −35% стоимости и сфабрикованный убыток.
  Теперь цена брокера, иначе цена покупки (`results["priced_at_cost"]`);
- дедупликация колонок: портфель, ДЕРЖАЩИЙ факторный ETF (`SPY` и др.), вообще
  не строил отчёт (`ValueError: Length mismatch`);
- SSOT `MAC3RiskEngine.proxy_for()` — отличает подмену бумаги от нормализации
  формата, поэтому `KSPI`→`KSPI.KZ` больше не выглядит как подмена.

**Что остаётся сделать в экране подтверждения ручного ввода (§5b E):** показать
подмены ОТДЕЛЬНОЙ строкой от `auto_resolved` (синонимы) — источник
`prefetch_market_data().proxy_map` либо `results["proxy_substitutions"]`, плюс
пометка «оценена по цене покупки» для `priced_at_cost`.

**H-2. Дубликаты со средневзвешенной ценой ломаются на разных валютах.**
План (§3.2) требует склеивать дубликаты со средневзвешенной ценой покупки.
Если две строки одной бумаги введены в РАЗНЫХ валютах (`KMGZ.KZ 100 12000` и
`KMGZ.KZ 50 25 USD`), усреднять сырые числа нельзя. Порядок обязателен:
сначала конвертация каждой строки, потом склейка.

**H-3. `Raw_Ticker` при авто-резолве синонима.**
Контракт: `Raw_Ticker` — «как ввёл пользователь». Если ввели «каспи», то
`Raw_Ticker="каспи"` попадёт в отчёт и в превью. Нужно решить явно: хранить
исходный ввод (честно, но в отчёте кириллица среди тикеров) или нормализованный
`KSPI` (чище, но теряется след ввода). Рекомендация — нормализованный в
`Raw_Ticker`, исходный — только в `auto_resolved` для экрана подтверждения.

**H-4. Пустой `Asset_Type` у нераспознанного класса.**
`_classify_instrument` для незнакомого тикера возвращает «Акция» по умолчанию.
Для ручного ввода это молчаливое допущение: введённый ETF или фонд будет
посчитан акцией в мандатной панели. Не блокер (то же поведение у демо), но
на экране подтверждения тип надо показывать — пользователь увидит и исправит.
