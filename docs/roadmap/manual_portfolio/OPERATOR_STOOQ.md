## 0. Одна страница: что именно делает человек

| Когда | Действие | Время |
|---|---|---|
| **Один раз** | скачать архив истории, распаковать, запустить бутстрап | ~40 мин, из них 35 — распаковка |
| **Каждый торговый вечер** | скачать `YYYYMMDD_d.txt`, положить в `inbox/`, запустить `ingest` | **~1 минута** |
| Раз в неделю | посмотреть сводку `ingest --report` | 2 минуты |
| Раз в квартал | перекачать архив истории заново (ре-бутстрап) | ~40 мин |

Всё остальное — работа кода. **Если регламент требует от человека чего-то
большего, это дефект кода, а не задача оператора.**

## 1. Роли и граница ответственности

```
 ОПЕРАТОР (человек, браузер)      КОД ingest (ручной запуск)       БОТ (Cloud Run)
 ─────────────────────────        ─────────────────────────        ────────────────
 скачал файл                      прочитал, отфильтровал,          открыл базу READ-ONLY
 положил в inbox/                 записал в SQLite,                посчитал отчёт
 запустил команду                 перенёс файл в applied/          в сеть НЕ ходил
```

Три правила границы, каждое существует ради конкретного отказа:

1. **Оператор не редактирует файлы.** Ни в Excel, ни в блокноте. Причина
   измерена: «почищенный» вручную файл невозможно отличить от испорченного, а
   фильтрация уже сделана кодом (§4.2). Присланная 2026-08-09 отфильтрованная
   выгрузка была корректна — но это везение, а не свойство процесса.
2. **Бот не пишет в базу.** Соединение открывается в режиме `ro`. Гонок нет
   по построению, а не по договорённости.
3. **Ingest не ходит в сеть.** Он читает только то, что лежит в `inbox/`.
   Скачивание — осознанное действие человека, потому что условия `/db/`
   юридически не проверены (§7).

## 2. Бутстрап: один раз

### 2.1 Что скачать

Со страницы <https://stooq.com/db/> — раздел **ASCII / Daily**:

| Пакет | Что внутри | Нужен |
|---|---|---|
| `d_us_txt.zip` | вся история дневных баров по США | **обязательно** |
| `d_world_txt.zip` | остальной мир: `.UK`, `.JP`, `.DE`, крипто `.V`, индексы `^` | пока нет; понадобится на шаге «мир» |

🔴 **Внутри `d_us_txt.zip` акции и ETF лежат в РАЗНЫХ подпапках:**

```
data/daily/us/nasdaq stocks/1/…      ← акции
data/daily/us/nasdaq etfs/…          ← фонды      ⚠️ легко не заметить
data/daily/us/nyse stocks/1/…
data/daily/us/nyse etfs/…
data/daily/us/nysemkt stocks/…
```

Ровно на этом обжёгся прошлый раунд: беглый просмотр показал одни `stocks`, и в
доке появилась запись «в пакете нет ни одного ETF» (`STOOQ_CONVENTION §3.6`).
Это было **неверно** — и опровергается файлом, который прислал сам владелец:
`vgit.us.txt` — это ETF Vanguard, 4 197 баров с 2009-11-23. **Качать один
архив, распаковывать целиком, подпапки не выбирать.**

### 2.2 Куда положить

```
/mnt/state/stooq/
├── archive/          ← сюда распакованный d_us_txt (структура папок как в zip)
├── inbox/            ← сюда дневные файлы YYYYMMDD_d.txt
├── applied/          ← ingest переносит сюда обработанные
├── rejected/         ← ingest кладёт сюда файлы, которые не прошли контроль
└── prices.sqlite     ← база; создаётся сама
```

### 2.3 Запуск

```bash
python scripts/stooq_ingest.py bootstrap --archive /mnt/state/stooq/archive
```

Бутстрап **идемпотентен**: повторный запуск на той же папке не портит базу и не
удваивает бары (первичный ключ `(market, ticker, trade_date)`).

### 2.4 Что должно быть на выходе

```
bootstrap завершён
  файлов прочитано ...... 11 842
  баров записано ........ 8 214 663
  окно ................. 2021-08-11 … 2026-08-07   (1825 кал. дней)
  отброшено:
    вне окна ............ 27 401 118
    нулевая заглушка ....      9 442
    битый OHLC ..........        118
  C-1 факторы .......... 10/10 ✅
  C-1 бенчмарки .........  3/3 ✅
```

**Строка `C-1 факторы 10/10` — это и есть допуск.** Если там не 10, ручной
режим включать нельзя: в профиле `STRICT` любая дыра среди факторных ETF даёт
`BLOCK` (`data_checks.py:428-441`), и пользователь получит отказ вместо отчёта.

## 3. Ежедневный цикл

```bash
# 1. Скачать со stooq.com/db/ файл YYYYMMDD_d.txt  (~700 КБ)
# 2. Положить его в inbox:
mv ~/Downloads/20260810_d.txt /mnt/state/stooq/inbox/
# 3. Применить:
python scripts/stooq_ingest.py apply
```

`apply` берёт **все** файлы из `inbox/`, сортирует по дате из имени и применяет
по порядку. Поэтому:

* **пропуск дня не ломает ничего** — накопите три файла и примените разом;
* **повторное применение безвредно** — тот же бар перезапишется собой;
* **порядок не важен** — `UPSERT` по `(market, ticker, date)` коммутативен.

### 3.1 Как выглядит нормальный день

```
apply 20260807_d.txt
  строк в файле ......... 12 002
  принято ............... 11 742     US-бумаги за 2026-08-07
  отброшено:
    чужая дата ..........      0
    индексы/FX ..........     56     ^AEX, ^DAX… — движок их не спрашивает
    крипто .V ...........    204     → market='CRYPTO', принято отдельно
  свежесть базы: US 0 торг. дней · CRYPTO 0 дней
```

### 3.2 Как выглядит НОРМАЛЬНАЯ суббота

```
apply 20260808_d.txt
  строк в файле .........    258
  принято ...............    202     только крипто
  отброшено:
    чужая дата ..........     56     индексы с датой 2026-08-07
  свежесть базы: US 1 торг. день (нормально: выходной)
```

🔴 **20 КБ вместо 700 КБ в выходные — это правильный файл, а не сбой.**
Замерено: суббота 2026-08-08 → 258 строк, из них 0 акций США. Крипто торгуется
круглосуточно и приходит; индексы приходят со вчерашней датой и отбрасываются
правилом «дата строки = дата файла».

### 3.3 Что НЕ является поломкой

| Наблюдение | Почему это норма |
|---|---|
| ~440 тикеров исчезли, ~440 появились за сутки (3.7 %) | в дневном срезе только бумаги, по которым **был сделка**. Варранты, SPAC-юниты, префы торгуются не каждый день |
| Саудовские индексы `^TASI`, `^MT30`, `^NOMUC` пропали в пятницу | биржа Эр-Рияда работает вс–чт; пятница — их выходной |
| Один тикер с битым OHLC (`^IPSA`, 06.08) | 1 строка на 11 999 = 0.008 %. Ingest её отбрасывает и считает в сводке |
| В файле есть строки с пустой датой и бары 2015 года | это последние бары мёртвых бумаг в мировой секции. Правило «дата = дата файла» снимает их автоматически |

### 3.4 Что ЯВЛЯЕТСЯ поломкой — и что делать

| Симптом | Смысл | Действие |
|---|---|---|
| `C-1 факторы 9/10` | у одного факторного ETF нет свежего бара | не выключать ручной режим; проверить тикер в файле руками. Если Stooq перестал его отдавать — это повод для `PHASE_10` (EODHD) |
| Будний день, а принято < 5 000 строк | усечённая выгрузка на стороне Stooq | **не применять**; скачать заново через час. Полу-день = дыра в истории у всех бумаг сразу |
| Файл ушёл в `rejected/` | не прошёл контроль формата | посмотреть причину в сводке; чаще всего — скачался HTML капчи вместо CSV |
| `свежесть базы: US 4 торг. дня` | четыре дня не применяли файлы | догрузить пропущенные дни; отчёт при таком лаге честно покажет `stale` |

## 4. Почему ручной фильтр в Excel — плохая идея

Владелец 2026-08-09 прислал **отфильтрованный** файл (только США + крипто), и он
был корректен. Тем не менее регламент требует присылать **сырой** файл, и вот
измеренная причина.

### 4.1 Два файла с одной датой оказались разными

| Файл за 2026-08-06 | Строк | Состав |
|---|---:|---|
| первая присылка | 12 474 | 8 408 US · 3 912 JP · 95 FX · 59 индексов · **0 крипто** |
| вторая (отфильтрованная) | 11 999 | **11 738 US** · 202 крипто · 59 индексов |

US-часть выросла на **3 330 бумаг** — то есть первый файл был не «тем же, но с
Японией», а другой выгрузкой. По содержимому этого не видно: имя одинаковое,
шапка одинаковая, даты одинаковые. **Человеческий шаг между источником и базой
не оставляет следа** — а база после него выглядит здоровой.

### 4.2 Фильтровать уже некому

Правило ingest № 1 («строка принимается, если её дата равна дате файла»)
на сыром файле сняло бы:

* **43 строки с пустой датой**,
* **148 строк с датами вплоть до 2015 года** — последние бары мёртвых бумаг,
* всё это без единого действия человека.

Ручной фильтр решает ту же задачу дороже и без записи о том, что именно
выброшено.

**Правило: качаем — кладём — применяем. Между «скачал» и «положил» ничего не
происходит.**

## 5. Ре-бутстрап: раз в квартал, и вот зачем

Дневные срезы дают только **новые** бары. Они не приносят:

* **ретроспективные корректировки** — если Stooq пересчитал историю после
  сплита или дивиденда, наша база останется со старыми числами;
* **бумаги, которых не было в универсуме** — новый листинг появится, но без
  истории до момента первого применённого файла.

Ре-бутстрап перекачивает архив и переписывает окно целиком. Он безопасен:
`UPSERT` по ключу, старые бары просто обновятся.

🔴 **Пока конвенция корректировок Stooq НЕ ИЗМЕРЕНА** (`STOOQ_CONVENTION §4`),
ре-бутстрап — единственная защита от расхождения истории с реальностью.
После замера конвенции интервал можно пересмотреть.

### 5.1 Как проверить, что шов не разъехался

Проверка занимает минуту и делает ровно то, что уже сделано вручную 2026-08-10:

```bash
python scripts/stooq_ingest.py verify-seam --date 2026-08-07
```

Она сравнивает бар из архива и бар из дневного среза за один и тот же день.
**Замер 2026-08-10: совпадение точное до последнего знака** на всех четырёх
живых бумагах (`VGIT`, `ZONE`, `SSS`, `SPSC`). Если однажды не совпадёт —
значит источник пересчитал историю, и нужен ре-бутстрап.

## 6. Мир после США: тот же регламент, другой пакет

Порядок расширения выбран так, чтобы каждый шаг был проверяемым:

| Шаг | Пакет | Что появляется | Что придётся решить |
|---|---|---|---|
| ✅ 1. США | `d_us_txt` | акции, ETF, 29 из 34 бумаг универсума | сделано |
| 2. Крипто | приходит в дневном срезе как `.V` | `BTC.V`, `ETH.V`, `SOL.V`, `BNB.V` — **все четыре есть** | торговый календарь 7/7 ≠ 5/7: пороги «свежести» разные |
| 3. Европа/Азия | `d_world_txt` | `.UK`, `.DE`, `.JP` | своя валюта у бумаги, свой календарь, свой FX |
| 4. Казахстан | **нет у Stooq** | — | `KZTK.KZ`, `KMGZ.KZ`, `KEGC.KZ` в выгрузке отсутствуют. Нужен другой источник или отказ по бумаге |

🔴 **Про `KAP.IL` и `HSBK.IL`.** Замер 2026-08-10 записал их как «не найдены» —
но искали формы `kap.il`, `kap`, `kap.us`. Это GDR на **Лондонской** бирже, а у
Stooq Лондон — суффикс **`.UK`**, и его в кандидатах не было; `.IL` у Stooq
означает Израиль. Вывод «в Stooq их нет» **не доказан**: проверять надо
`kap.uk` / `hsbk.uk` в пакете `d_world_txt`.

## 7. 🔴 Юридический пункт — до включения в проде

Условия использования `stooq.com/db/` **не проверены**. До включения
`MANUAL_PORTFOLIO_ENABLED=true` в проде нужно прочитать условия сайта и
зафиксировать в `STOOQ_CONVENTION §3.2` один из трёх ответов:

1. bulk-выгрузка разрешена для нашего сценария → работаем;
2. разрешена с ограничением (некоммерческое / атрибуция) → выполняем условие;
3. запрещена → переключаемся на `PHASE_10` (EODHD, платный, условия ясны).

Это тот же класс требования, что I-12 для Tradernet: **источник данных имеет
правовой режим, и он не выводится из технической доступности файла.**
