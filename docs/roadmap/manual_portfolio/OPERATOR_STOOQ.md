## Выходные дни грузить не нужно

**Короткий ответ: нет.** Субботний и воскресный срезы Stooq содержат **ноль
US-баров** (замер 2026-08-08: 258 строк, все крипто). Грузить нечего, а
пропуск выходных ничего не ломает:

* календарь рынка выводится ИЗ ДАННЫХ — суббота не станет сессией US, если
  US-баров в ней нет;
* свежесть бумаги считается в ТОРГОВЫХ днях её рынка, поэтому пропущенная
  суббота не старит US-бумагу ни на день;
* правило 9 загрузчика имеет форму «0 < принято < порога» — ноль US-баров
  читается как закрытый рынок, а не как недокачанный файл.

Применить выходной файл не вредно (он просто добавит крипто-бары), но и
пользы для книги без крипто не даёт.

🔴 **Исключение — крипто.** Тикеры с суффиксом `.V` торгуются 7 дней в
неделю. Если в портфеле есть крипто, выходные грузить ОБЯЗАТЕЛЬНО: иначе в
ряду появятся настоящие дыры, и после 5 пропущенных торговых дней бумага
выпадет из расчёта.

⚠️ **Что действительно нельзя пропускать — БУДНИЕ дни.** Отдельный гард
считает возраст всего рынка в КАЛЕНДАРНЫХ днях с порогом 7. Выходные съедают
2 дня из них бесплатно, поэтому после пятничной заливки ручной отчёт
блокируется со следующей **субботы**, если за неделю не залито ничего.
Практическое правило: пропустить подряд можно не больше двух-трёх будних дней.

## 1. Почему именно так, а не «всё в облаке»

Решение принято по замерам (`PHASE_08B §3.1a`), три причины:

1. **Архив истории в облако не едет.** 0.84 ГБ и 11 842 файла: через gcsfuse
   это часы, на локальном диске — минуты. Архив холодный, он нужен раз в квартал.
2. **`/tmp` на Cloud Run — это оперативная память** при лимите 2 GiB
   (`freedom_portfolio/history.py:636`). Бот копирует базу к себе, и 60 МБ он
   не заметит, а полную выгрузку US (**≈900 МБ**) не переживёт.
3. **Писать SQLite поверх объектного хранилища нельзя** — файловые блокировки
   там не работают. Разбор остаётся там, где есть настоящая файловая система.

Деньги в этом решении не участвуют: бакет Standard в `us-central1` с
бесплатным лимитом 5 ГБ (это записано в `cloudbuild.yaml:20-24`), а рабочий
набор укладывается в него с запасом в сотни раз.

## 3. ШАГ 1 — окружение

Нужен **Python 3.11 или новее**. Проверка:

```bash
python3 --version
```

### 3.1 Сколько зависимостей ставить

Загрузчик написан на **чистой стандартной библиотеке** — это проверяется
тестом (`test_ingest_library_needs_no_third_party`), а не обещано в
комментарии. Поэтому:

| Что вы хотите | Что ставить |
|---|---|
| ежедневный `apply` | **ничего**; хватит голого Python |
| `bootstrap` рабочего набора, допуск C-1, `verify-universe` | `pip install pandas` |
| запускать тесты проекта | `pip install -r requirements.txt` (тяжело: sklearn, aiogram, anthropic) |

**Ставьте pandas** — второй вариант, он же рабочий:

```bash
python3 -m venv ~/ramp-venv
source ~/ramp-venv/bin/activate
pip install pandas
```

🔴 **Windows — другая команда, а не другой слэш** (§3.3): окружение создаётся
**рядом с домашним каталогом, а не внутри репозитория**, и PowerShell требует
файл с расширением:

```powershell
python -m venv C:\Users\User\ramp-venv
C:\Users\User\ramp-venv\Scripts\Activate.ps1
pip install pandas
```

Почему граница проходит именно здесь. Список факторных ETF — это знание
ДВИЖКА, оно живёт в `finance/data_checks.py`, а тот тянет pandas и numpy.
Копировать список в скрипт нельзя: получился бы второй справочник, который
однажды разойдётся с первым молча. Поэтому:

* `apply` работает на голом Python и лишь честно печатает
  `⚠️ C-1 НЕ ПРОВЕРЕН` вместо строки допуска;
* `bootstrap` **без pandas откажется** и скажет, что делать: поставить pandas
  либо задать бумаги вручную через `--symbols`. Молча уйти в `--all` он не
  вправе — это ≈900 МБ вместо 60, то есть OOM контейнера.

Молча пропустить C-1 код не имеет права ни в одном режиме: это ваш допуск
(§6.1), и его пропуск читался бы как «проверено, всё хорошо».

### 3.2 Рабочие каталоги

```bash
mkdir -p ~/ramp-stooq/{archive,inbox,applied,rejected}
export STOOQ_ROOT=~/ramp-stooq
```

`STOOQ_ROOT` избавляет от длинных путей в каждой команде.

### 3.3 Windows — то же самое, четыре отличия

Все команды регламента работают на Windows без изменений; меняется только
запись путей и переменных.

```powershell
# PowerShell
C:\Users\User\ramp-venv\Scripts\Activate.ps1
$env:STOOQ_ROOT = "C:\Users\User\ramp-stooq"
cd C:\Users\User\ramp-fresh
python scripts\stooq_ingest.py bootstrap --archive "$env:STOOQ_ROOT\archive"
```

```bat
:: cmd.exe
C:\Users\User\ramp-venv\Scripts\activate.bat
set STOOQ_ROOT=C:\Users\User\ramp-stooq
cd C:\Users\User\ramp-fresh
python scripts\stooq_ingest.py bootstrap --archive "%STOOQ_ROOT%\archive"
```

| Отличие | Что делать |
|---|---|
| `python3` → **`python`** | в Windows команда называется так |
| `$STOOQ_ROOT` → `$env:STOOQ_ROOT` (PS) или `%STOOQ_ROOT%` (cmd) | синтаксис оболочки |
| `source ~/ramp-venv/bin/activate` → `C:\Users\User\ramp-venv\Scripts\Activate.ps1` | путь активации venv |
| Пути с пробелами (`nasdaq etfs`) | кавычки: `--archive "C:\Users\User\ramp-stooq\archive"` |

🔴 **Про активацию venv — две ошибки, обе стоили времени оператору.**

1. **Окружение НЕ внутри репозитория.** `~/ramp-venv` разворачивается в
   `C:\Users\User\ramp-venv` — уровнем ВЫШЕ `ramp-fresh`. Относительная запись
   `.\ramp-venv\Scripts\…` из каталога проекта не найдёт ничего: репозиторий и
   рабочее окружение оператора живут раздельно намеренно (§2.2 — репозиторий
   переклонируется, окружение остаётся).
2. **PowerShell не запускает `activate` без расширения.** Ему нужен
   `Activate.ps1`; `activate` без расширения — это скрипт для bash, а
   `activate.bat` — для `cmd.exe`. Три разных файла в одной папке, и оболочка
   молча не найдёт чужой.

Если PowerShell откажет с `выполнение сценариев отключено в этой системе`,
политика запуска разрешается для текущего пользователя один раз:

```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```

Признак, что окружение активно, — префикс `(ramp-venv)` в приглашении строки.

🔴 **Про «кракозябры» и падения вывода.** Консоль `cmd.exe` в русской Windows
работает в `cp866`, PowerShell 5.1 — в `cp1251`. Ни одна из них не кодирует
символы `🔴`, `✅`, `⚠️`, `→`, `≈`, `—`, которых в выводе команд десятки;
Python в такой ситуации **не рисует квадратики, а падает**
с `UnicodeEncodeError`. Загрузчик это обходит сам — переключает свой вывод в
UTF-8 при старте (`_make_console_utf8_safe`, покрыто тестом на потоке cp866),
поэтому команда доходит до конца в любой консоли. Если значки всё же
отображаются квадратиками, текст от этого не портится; хотите красиво —
Windows Terminal или PowerShell 7.

## 5. ШАГ 3 — бутстрап: собрать базу

```bash
cd ~/ramp-fresh
python scripts/stooq_ingest.py bootstrap --archive $STOOQ_ROOT/archive
```

Команда собирает базу из двух частей, и обе обязательны:

| Часть | Что это | Сколько |
|---|---|---|
| **ядро** | 10 факторных ETF + 3 бенчмарка — из кода движка | 13 бумаг |
| **ликвидный универсум** | бумаги, которые пользователь может ввести | до 800 (флаг) |

> 🔴 **Почему одного ядра НЕДОСТАТОЧНО — и почему прежняя редакция этого
> раздела была неверна** (`AUDIT §−85`). До 2026-08-11 команда грузила только
> ядро: 13 бумаг, ≈1 МБ. Такая база проходит допуск `C-1 10/10` и при этом
> **не строит ни одного отчёта** — бумаг пользователя в ней нет, `C-8`
> блокирует по доле непокрытой стоимости. Прежний §5.2 предлагал добирать
> бумаги вручную командой `backfill`, но узнать их заранее нельзя: ручной ввод
> на то и ручной. План (`PHASE_08B §3.1`) закладывал 0.6–1.0 млн баров и прямо
> отмечал «нужен механизм добора» — механизм появился только сейчас.

**Отбор идёт по ИЗМЕРЕННЫМ признакам, а не по списку тикеров.** Захардкоженный
«топ-500 ликвидных» устарел бы молча — первым же делистингом или IPO, и узнали
бы мы об этом из отчёта пользователя. Признаки пересчитываются на каждом
ре-бутстрапе:

| Флаг | По умолчанию | Что отсекает |
|---|---|---|
| `--min-bars` | **авто** | короткую историю: она схлопывает окно регрессии ВСЕЙ панели (F-15/F-21), то есть одна молодая бумага портит чужие числа |
| `--stale-days` | 10 | делистингованные: их последняя цена приехала бы как сегодняшняя (замер `tph.us`) |
| `--min-turnover` | 1 000 000 | неликвид: ряд из повторов даёт ложно НИЗКУЮ волатильность, а это выглядит как хорошая новость |
| `--universe-limit` | 800 | потолок РАЗМЕРА, не качества — отсекается наименее ликвидное |

> 🔴 **Почему порог истории «авто», а не число** (`AUDIT §−87`). В первой
> редакции стояло 1260 баров — и это обнулило универсум на живой выгрузке.
> Окно в 1825 календарных дней даёт 1304 будних дня минус праздники, то есть
> около **1252** баров; замер оператора на своём архиве дал ровно 1252. Порог
> оказался выше физически достижимого, отсеял ВСЕХ кандидатов, а команда
> напечатала «рабочий набор: 13 бумаг» — не соврав ни словом. Тринадцать
> уцелевших это ядро, которое добавляется безусловно, и потому дефект выглядел
> как «сканер не видит подпапок».
>
> Теперь эталон берётся из данных: порог = 90 % от истории самой полной бумаги
> АРХИВА. Сколько торговых дней в окне на самом деле, знает только рынок — там
> праздники, полудни и разные биржи; считать это в коде значит заводить второй
> календарь, который разойдётся с данными молча.

**Команда всегда печатает, почему бумаг отобрано именно столько:**

```
  померено бумаг ........ 11842
  порог истории ......... 1126 баров (у самой полной бумаги архива — 1252)
    короткая история .... 3401
    давно не торгуются .. 512
    мало оборота ........ 7129
    не влезли в потолок . 0
  ОТОБРАНО .............. 800
```

Если отобрано 0 — виновный критерий назван прямо в этой таблице, и ослаблять
надо именно его. Гадать про пути и слэши не нужно: строка «померено бумаг»
отвечает на вопрос, нашёл ли сканер архив, отдельно от вопроса, что он отсеял.

Размер базы считается прямо: **75 КБ на бумагу** (замер на 65 000 баров).

| Набор | Бумаг | База | Годится для прода |
|---|---|---|---|
| `--core-only` | 13 | ≈1 МБ | ❌ отчёт не построится |
| по умолчанию | ≈813 | **≈60 МБ** | ✅ |
| `--universe-limit 3000` | ≈3000 | ≈230 МБ | ✅, если не жалко трафика |
| `--all` | ≈11 700 | **≈900 МБ** | ❌ `/tmp` в Cloud Run — это RAM при лимите 2 GiB |

Первый бутстрап дольше остальных: команда один раз читает ВЕСЬ архив, чтобы
померить ликвидность (≈12 000 файлов, единицы минут). Ежедневный `apply`
архив не трогает вовсе.

База создаётся в `$STOOQ_ROOT/prices.sqlite` — там же, где папки. Один корень
управляет всем, поэтому собранный файл лежит ровно там, откуда вы его потом
зальёте (§7). Переопределить путь можно флагом `--db` или переменной
`STOOQ_DB_PATH`.

### 5.1 Как выглядит правильный результат

Форма вывода — настоящая, конкретные числа зависят от вашей выгрузки:

```
ядро: 13 бумаг · сканирую архив, чтобы добрать ликвидные (потолок 800)…
рабочий набор: 813 бумаг (≈60 МБ базы)
bootstrap завершён
  файлов обработано ..... 813
  строк прочитано ....... …
  баров записано ........ ≈ 1 020 000   (813 бумаг × ≈1 260 торговых дней)
  инструментов заведено . 813
  отброшено:
    вне окна .................. …       (история глубже 5 лет)
  C-1 факторы ........... 10/10 ✅
  C-1 бенчмарки ......... 3/3
```

**Строка `C-1 факторы 10/10` — это допуск, но НЕ достаточное условие.** Если
там меньше десяти, ручной режим включать нельзя: в профиле `STRICT` потеря
любого факторного ETF даёт `BLOCK` (`data_checks.py:428-441`), и пользователь
получит отказ вместо отчёта. Но и 10/10 при пустом универсуме означает лишь,
что модель построится — по чужому портфелю, не по вашему.

`вне окна` — не ошибка: движок работает на окне 1825 календарных дней (≈5
лет), а история в архиве уходит на 16 лет назад. Лишнее не хранится.

### 5.2 Добрать бумагу, которой всё же не хватило

Универсум отсекает неликвид — значит бумага пользователя может в него не
попасть на законных основаниях. Такой случай виден в отчёте честно (`C-8`
называет непокрытую долю), и лечится точечно, из того же архива и без сети:

```bash
python scripts/stooq_ingest.py backfill --ticker AAPL.US,MSFT.US
```

После добора базу надо перезалить (§7) — иначе бот продолжит читать прежнюю.

## 8. Ежедневный цикл

### 8.0 🟢 Через бота-загрузчика — основной путь

С 2026-08-20 ежедневный цикл не требует компьютера вовсе:

```
1. скачать со stooq.com/db/ файл YYYYMMDD_d.txt   (~700 КБ) — ЭТО АКЦИИ
2. скачать дневной пакет ETF за тот же день      — БЕЗ НЕГО ФАЙЛ НЕПОЛНЫЙ
3. слить их в один файл (команды ниже)
4. проверить одной командой, что ETF на месте
5. переслать в чат бота-загрузчика и прочитать сводку
```

### 🔴 Шаг 2 пропускать НЕЛЬЗЯ: в дневном пакете акций НЕТ НИ ОДНОГО ETF

Это ИЗМЕРЕНО дважды, и оба раза дорого:

* при бутстрапе (`STOOQ_CONVENTION §3.6`) — 12 известных ETF отсутствовали, 10
  известных акций были на месте; допуск C-1 дал 0 из 10;
* в проде 24–28.08 (`AUDIT §−113`) — пять дней подряд срез клал **631 бар в
  базу из 803 бумаг**, и все 13 тикеров C-1 замерли на первом же дне.

Причина одна и та же и она НЕ в боте: наш универсум — это в основном ETF
(10 факторов + 3 бенчмарка + прокси), а дневной пакет акций их не содержит. В
архиве `d_us_txt.zip` они лежат в отдельных подпапках (`nasdaq etfs/`,
`nyse etfs/`, §4) — у дневных файлов ровно то же разделение.

**Проверка перед отправкой — 5 секунд и одна команда:**

```bash
grep -ic "^SPY\.US," 20260828_d.txt     # 1 — ETF на месте, 0 — файл неполный
```

**Слияние (шапка берётся из ПЕРВОГО файла, поэтому она обязана совпадать):**

```bash
STOCKS=20260828_d.txt
ETFS=20260828_etf_d.txt                  # имя зависит от того, что скачали

head -1 "$STOCKS"; head -1 "$ETFS"       # шапки обязаны быть одинаковыми
tail -n +2 "$ETFS" >> "$STOCKS"          # приклеить строки ETF без второй шапки
grep -ic "^SPY\.US," "$STOCKS"          # ждём 1
```

🔴 **Слать пакет ETF отдельным файлом, скорее всего, не выйдет.** Правило 9
(`STOOQ_MIN_US_ROWS`, по умолчанию 5000) считает будний файл с
`0 < принято < 5000` недокачанным, а ETF США — 3–4 тыс. строк. Посмотрите
`wc -l`: если строк ≥ 5000, можно слать вторым файлом; если меньше — только
слияние.

**Как убедиться, что вылечилось.** В сводке `баров записано` обязано быть
близко к числу бумаг базы (`… из 803`), строки «без бара за …» быть не должно,
а `C-1 факторы` — с зелёной галочкой. `/status` печатает то же самое полем
`свежих`.

### 8.0б Затычка, если пакета ETF под рукой нет

Не замена процессу — способ не потерять день, пока пакет ищется. Скрипт читает
опубликованную базу, находит бумаги БЕЗ бара за нужный день и тянет их со
Stooq потикерно, дописывая строки в тот же файл среза:

```bash
gcloud storage cp gs://ramp-bot-state/stooq/prices.sqlite .
python3 scripts/stooq_topup.py prices.sqlite 20260828 20260828_d.txt
grep -ic "^SPY\.US," 20260828_d.txt      # ждём 1
```

Дальше файл пересылается боту как обычно. Отказ источника приходит ТЕКСТОМ с
кодом 200 («Exceeded the daily hits limit»), поэтому скрипт проверяет шапку
ответа и такие строки в файл не пишет — он честно скажет, сколько бумаг
источник не отдал.

Бот сам применяет 9 правил фильтра, публикует базу и печатает ту же сводку,
что и команда `apply` ниже, — форма совпадает намеренно, чтобы регламент и бот
говорили про одно событие одинаково.

| Команда бота | Зачем |
|---|---|
| `/status` | поколение базы, свежесть рынков, **сколько дней до блокировки ручного тира** |
| `/missing` | какие дневные файлы переслать после ре-бутстрапа |
| `/universe` | допуск C-1 с глубиной истории по каждому фактору |
| `/check AAPL.US` | найдёт ли отчёт эту бумагу и под какой формой символа |
| `/prune` | вычистить бумаги с обрывочной историей (сначала `--dry-run`) |

🔴 **Бутстрап и ре-бутстрап через чат невозможны**: архив истории весит 0.84 ГБ,
Telegram отдаёт боту не больше 20 МБ. Сборка базы с нуля остаётся здесь, §5.

### 8.0a Запасной путь — те же три команды

Он не «устаревший», а именно запасной: пока бот недоступен (деплой, сбой),
цикл обязан работать без него. Бот это учитывает — день, применённый через
CLI, он видит в базе и молча досинхронизирует свой журнал, не поднимая тревогу.

```bash
# 1. Скачать со stooq.com/db/ файл YYYYMMDD_d.txt  (~700 КБ, 5 секунд)
mv ~/Downloads/20260810_d.txt $STOOQ_ROOT/inbox/

# 2. Применить локально (0.2 с на файл — замерено)
cd ~/ramp-fresh && python scripts/stooq_ingest.py apply

# 3. Опубликовать
gcloud storage cp $STOOQ_ROOT/prices.sqlite gs://ramp-bot-state/stooq/prices.sqlite
```

`apply` берёт **все** файлы из `inbox/`, сортирует по дате из имени и
применяет по порядку. Поэтому:

* **пропуск дня не ломает ничего** — накопите три файла и примените разом;
* **повторное применение безвредно** — тот же бар перезапишется собой
  (проверено тестом: база остаётся побитово прежней);
* **порядок не важен** — запись по ключу `(инструмент, дата)` коммутативна.

### 8.1 Нормальный будний день

```
apply завершён
  файлов обработано ..... 1
  строк прочитано ....... 12 002
  баров записано ........ 11 942
  отброшено:
    индекс/FX (пропуск)....... 56
    плоская заглушка..........  4
  C-1 факторы ........... 10/10 ✅
```

### 8.2 Нормальная суббота

Файл на **20 КБ вместо 700 КБ — это правильный файл, а не сбой.** Замерено:
суббота 2026-08-08 → 258 строк, из них **ноль** американских акций. Крипта
торгуется круглосуточно и приходит; индексы приходят со вчерашней датой и
отбрасываются правилом «дата строки = дата файла».

### 8.3 Что НЕ является поломкой

| Наблюдение | Почему это норма |
|---|---|
| ~440 тикеров исчезли и ~440 появились за сутки (3.7 %) | в дневном срезе только бумаги, по которым **была сделка**. Варранты, SPAC-юниты и префы торгуются не каждый день |
| саудовские индексы пропали в пятницу | биржа Эр-Рияда работает вс–чт; пятница у них выходной |
| одна строка с битым OHLC | замер: 1 на 11 999 (0.008 %). Загрузчик её отбрасывает и считает в сводке |
| строки с пустой датой и бары 2015 года в сыром файле | последние бары мёртвых бумаг; правило «дата = дата файла» снимает их само |
| `плоская заглушка: 4` | бар без объёма и без размаха — цена без сделки; в расчёте риска она была бы ложным нулём волатильности |

### 8.4 Что поломка — и что делать

| Симптом | Смысл | Действие |
|---|---|---|
| `🔴 ФАЙЛ ОТВЕРГНУТ ЦЕЛИКОМ … недокачанным` | скачалась половина файла | скачать заново через час. Загрузчик **не тронул базу** — это его работа, не ваша |
| файл уехал в `rejected/` | не прошёл контроль формата | чаще всего скачалась HTML-страница капчи вместо CSV. Открыть файл глазами, скачать заново |
| `C-1 факторы 9/10` | у факторного ETF нет свежего бара | не паниковать и ничего не выключать; проверить тикер в файле. Если Stooq перестал его отдавать — это повод для `PHASE_10` (платный источник) |
| будний день, а принято < 5 000 строк | усечённая выгрузка на стороне Stooq | сработает автоматически: файл будет отвергнут целиком |

## 9. Ре-бутстрап: раз в квартал

Дневные срезы приносят только **новые** бары. Они не приносят:

* **ретроспективные корректировки** — если Stooq пересчитал историю после
  сплита, у нас останутся старые числа;
* **историю бумаг, появившихся позже** первого применённого файла.

```bash
# перекачать d_us_txt.zip, распаковать поверх archive/, затем:
python scripts/stooq_ingest.py bootstrap --archive $STOOQ_ROOT/archive
python scripts/stooq_ingest.py verify-seam --date <последний торговый день>
# залить базу (§7), затем СПРОСИТЬ БОТА:
#   /missing  → он назовёт дни, которых в свежесобранной базе нет
#   переслать эти файлы из applied/ — порядок не важен, повтор безвреден
```

Ре-бутстрап безопасен: запись идёт по ключу, старые бары просто обновляются.

🔴 **Но он стирает дни, которые бот применил после того, как вы скачали
архив.** Архив квартальный, дельты свежие — в архиве их просто нет. Отдельного
ритуала для этого не заведено намеренно: бот сам сравнивает свой журнал с
базой и называет пропавшие дни. Команда `/missing` печатает тот же список по
требованию.

🔴 Пока **конвенция корректировок Stooq не измерена**
(`STOOQ_CONVENTION §4`), ре-бутстрап — единственная защита от расхождения
истории с реальностью.

## 11. 🔴 Чего делать НЕЛЬЗЯ — и что сломается

Это главный раздел регламента. Каждый запрет — про конкретную поломку, а не
про аккуратность.

### 11.1 Не редактировать файлы Stooq руками

Ни в Excel, ни в блокноте. Фильтрация уже сделана кодом.

**Что ломается.** Присланные 2026-08-06 две выгрузки за ОДНУ дату отличались
на **3 330 бумаг** — при одинаковом имени, одинаковой шапке и одинаковых
датах. По содержимому подмену не отличить. Шаг человека между источником и
базой не оставляет следа, а база после него выглядит здоровой.

Сырой файл обрабатывается без потерь: правило «дата строки = дата файла»
снимает и 43 строки с пустой датой, и 148 баров вплоть до 2015 года.

### 11.2 Не заливать в бакет исходные `.txt`

Заманчиво лить дневные файлы в облако и разбирать их там.

**Что ломается.** Писателем SQLite становится процесс поверх gcsfuse, где
файловые блокировки не работают, — ради задачи, которая локально занимает
0.2 секунды. В бакет едет **только собранная база**.

### 11.3 Не грузить полную выгрузку (`--all`) в продовую базу

**Что ломается.** 704 МБ. `/tmp` на Cloud Run — это RAM при лимите 2 GiB, а
там ещё pandas и sklearn. Контейнер уйдёт в OOM, и это положит **весь бот**, а
не только ручной режим.

### 11.4 Не трогать `tokenomics.db` и `users_vault.db`

Они лежат в том же бакете. В первом — балансы токенов, во втором —
зашифрованные ключи брокера пользователей.

**Что ломается.** Всё. Восстановления нет.

### 11.5 Не включать `MANUAL_PORTFOLIO_ENABLED` раньше гейта

**Что ломается.** Провайдера цен ещё нет: `provider_for_source("manual")`
бросает `ProviderUnavailable`. Пользователь, выбравший ручной ввод, упрётся в
отказ. Сегодня это безопасно (флаг выключен и есть явная ветка-отказ без
списания токена), но включать флаг до готовности провайдера — значит
поломать флоу руками.

### 11.6 Не менять переменные окружения Cloud Run по одной

Когда придёт время добавить `STOOQ_DB_PATH`, его надо **дописать в
существующую строку** `--set-env-vars` в `cloudbuild.yaml`.

**Что ломается.** `gcloud run deploy --set-env-vars` заменяет **весь набор**
переменных целиком. Эта грабля уже сработала: выставленный руками в консоли
флаг Premium V2 стирался на следующем деплое, и прод месяцами отдавал старый
шаблон отчёта (`cloudbuild.yaml:118-126`).

### 11.7 Не собирать базу на двух машинах одновременно

**Что ломается.** Не база — она у каждого своя. Ломается бакет: вторая
загрузка молча затрёт первую, и часть дней исчезнет. Оператор должен быть один.

🟢 **С появлением бота у этого правила есть МЕХАНИЗМ, а не только просьба.**
Бот публикует базу с проверкой поколения (compare-and-swap): если объект
изменился, пока он применял файл, публикация отвергается, и бот громко
спрашивает, не заливали ли вы базу вручную. Правило от этого не отменяется —
защищена только одна сторона: `gcloud storage cp` по-прежнему затирает всё
молча.

### 11.8 Не переименовывать дневные файлы

Имя `YYYYMMDD_d.txt` — не украшение: из него берётся дата, с которой
сверяются строки. Файл без даты в имени загрузчик отвергнет целиком, и это
правильно: без неё главное правило фильтра неприменимо.

### 11.9 Не коммитить данные в git

`.gitignore` уже отсекает `*.sqlite`, `*.db` и `data/stooq/`. Но лучше просто
не коммитить из рабочей папки оператора вообще — она для данных, а не для кода.

## 12. Диагностика

| Сообщение | Что значит | Что делать |
|---|---|---|
| `нет шапки <TICKER>` | скачался HTML капчи вместо CSV | открыть файл глазами, скачать заново |
| `имя файла не содержит дату` | файл переименован или это файл истории | вернуть имя вида `20260810_d.txt` |
| `базы котировок нет по пути …` | ещё не было бутстрапа | §5 |
| `⚠️ C-1 НЕ ПРОВЕРЕН: pandas не установлен` | база наполнена, допуск не подтверждён | `pip install pandas`, повторить команду |
| `в … нет файлов вида YYYYMMDD_d.txt` | пустой `inbox/` | положить файл |
| `🔴 шов на …: расхождений N` | Stooq пересчитал историю | ре-бутстрап (§9) |

### Ш7 · Живая проверка отчёта — новый шаг, и он главный

Ради этого всё и делалось: убедиться, что по вашей базе строится ОТЧЁТ, а не
только проходят проверки.

```bash

PYTHONPATH=src python -m pytest tests/test_manual_freedom_parity.py -q
```

Этот тест строит два отчёта на одних ценах — ручной и брокерский — и требует,
чтобы они совпали во всех 36 ключах контракта, кроме подписи источника и
профиля чекеров. Он не трогает вашу базу (собирает свою), но подтверждает, что
код на вашей машине работоспособен целиком.

Затем — отчёт по СВОЕЙ книге, глазами: 5 бумаг, сравнить риск-индекс, Sharpe и
MaxDD с брокерским отчётом по той же книге. Расхождение обязано быть объяснимо
разными ценами закрытия, а не выглядеть случайным.


|---|---|---|
| `STOOQ_DB_PATH` | `/mnt/state/stooq/prices.sqlite` | где лежит база |
| `STOOQ_LOCAL_COPY_DIR` | `/tmp/ramp-stooq` | куда бот кладёт локальную копию |

🔴 Копия — не оптимизация «на будущее». База лежит на gcsfuse, а SQLite читает
файл случайным доступом: каждая страница превращается в отдельный
range-запрос к объектному хранилищу, а один отчёт делает их сотни. Копия
делается один раз на контейнер и обновляется сама, как только вы зальёте новую
базу (сверяются размер и время правки). Дефолт каталога уже правильный —
переменная нужна, только если вы хотите другой путь.

### Ш9 · Три дня ежедневного цикла

`apply` каждый торговый вечер (§8). Папка `rejected/` обязана оставаться
пустой три дня подряд — только после этого цикл считается проверенным.

🔴 **Если вы запускали `apply` версией до 2026-08-11 — базу надо вычистить.**
Прежняя редакция заводила инструмент на КАЖДЫЙ символ дневного среза, а там все
~12 000 тикеров США: первый же запуск добавлял ~11 000 бумаг с историей в один
день (`AUDIT §−88`). Признак — строка `инструментов заведено` намного больше
нуля при обычном `apply`.

```bash
python scripts/stooq_ingest.py prune --dry-run     # посмотреть, что уйдёт
python scripts/stooq_ingest.py prune               # вычистить и сжать файл
```

`prune` удаляет бумаги с обрывочной историей по тому же порогу, что и отбор
универсума, и НИКОГДА не трогает ядро. Ре-бутстрап тоже чинит, но стоит
нескольких минут скана; `prune` архив не читает вовсе. После чистки базу надо
перезалить (Ш8).

В сводке нормального `apply` теперь есть строка `вне рабочего набора` — это
бумаги дневного среза, которых нет в вашей базе. Число в тысячах здесь **норма**:
состав базы определяет бутстрап, дельта только дописывает бары.
