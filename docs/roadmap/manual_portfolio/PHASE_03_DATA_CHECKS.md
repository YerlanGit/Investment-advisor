## 1. Цель и главное отличие от задания

Три блока проверок между провайдером и `analyze_all`. Уровни: **BLOCK** — отказ,
токен не списан; **DEGRADE** — расчёт идёт, факт попадает в CoVe и `data_lineage`;
**PASS** — молча.

**Отличие от задания — профили строгости** (`README.md §2 К-4`, `PHASE_00 §3`).
Задание объявляет C-1/C-2/C-5/C-6 безусловными BLOCK для всех источников. В коде это
означало бы блокировку отчётов, которые сегодня успешно строятся:

| Что задание объявляет BLOCK | Что движок делает сегодня | Во сколько раз строже |
|---|---|---|
| C-1: потеря ≥1 фактор-ETF | `present_factors` собирается из доехавших; отказ только если не доехало НИ ОДНОГО (`investment_logic.py:903-906`) | качественно строже |
| C-2: окно < 252 наблюдений | `min_obs = max(2·K, 30)` = 30 при 10 факторах (`931`); `MIN_OVERLAP_TDAYS = 60` (`period_returns.py:150`) | ×4…×8 |
| C-6: матрица не PD | Движок делает PSD-проекцию и продолжает (`investment_logic.py:300-304`) | качественно строже |

Поэтому строгие пороги применяются к `manual` (профиль `STRICT`), а `freedom`/`demo`
получают `LEGACY` — ровно те пороги, которые движок реализует сейчас. Это и есть
механизм, которым держатся **I-5, I-9 и I-10**.

## 2. Форма результата

```python
class CheckLevel(str, Enum):
    PASS = "pass"; DEGRADE = "degrade"; BLOCK = "block"

class CheckProfile(str, Enum):
    LEGACY = "legacy"    # freedom / demo — «не хуже, чем сегодня»
    STRICT = "strict"    # manual

@dataclass(frozen=True)
class CheckFinding:
    id:       str                 # "C-8"
    level:    CheckLevel
    ticker:   str | None          # None — проверка портфельного уровня
    message:  str                 # человеческий текст, БЕЗ str(exc) и без секретов
    detail:   dict                # числа для CoVe и структурного лога

@dataclass
class DataQualityReport:
    profile:  CheckProfile
    findings: list[CheckFinding]
    @property
    def blocked(self) -> bool: ...
    def user_message(self) -> str: ...      # текст отказа пользователю
    def lineage_rows(self) -> list[dict]:   # DEGRADE → строки CoVe
```

**Чекеры — данные, а не разбросанные `if`** (гейт §10 задания): каждая проверка —
запись реестра `CHECKS: list[CheckSpec]` с полями `id`, `block`, `applies_to`,
`thresholds: dict[CheckProfile, float]`, `fn`. Добавление проверки = строка в реестре.

## 3. Реестр проверок

### Блок A — целостность выгрузки (одинаково в обоих профилях)

| ID | Проверка | Уровень |
|---|---|---|
| A-1 | Тело — CSV: первая строка совпадает с ожидаемым заголовком. Маркеры `Exceeded the daily hits limit`, `apikey`, `<html` в начале тела → отказ | BLOCK по тикеру |
| A-2 | HTTP 200 и отсутствие редиректа | BLOCK по тикеру |
| A-3 | Размер тела в пределах потолка S-3 | BLOCK по тикеру |
| A-4 | Число строк > 0 после парсинга | BLOCK по тикеру |
| A-5 | Кодировка и BOM обработаны, разделитель определён однозначно | BLOCK по тикеру |
| A-6 | Все обязательные колонки на месте, `Close` приводится к float без потерь | BLOCK по тикеру |

Блок A специфичен для HTTP/CSV-провайдеров и до Фазы 9 не имеет производителя данных.
Реализуется здесь целиком, тестируется на синтетических телах ответов — иначе Фаза 9
войдёт в работу без сетки безопасности.

### Блок B — корректность ряда (одинаково в обоих профилях)

| ID | Проверка | Порог | Уровень |
|---|---|---|---|
| B-1 | `DatetimeIndex`, строго возрастающий, без дублей дат | — | BLOCK по тикеру |
| B-2 | Все значения конечны и > 0 | — | BLOCK по тикеру |
| B-3 | Дисперсия ряда > 0 | — | BLOCK по тикеру |
| B-4 | Свежесть: последняя дата не старше 5 торговых дней | >5 | DEGRADE |
| B-5 | Нет разрыва длиннее 10 торговых дней внутри окна | >10 | DEGRADE |
| B-6 | Доля дней с \|log-доходностью\| > 0.4 после слоёв коррекции | >0.1% | DEGRADE |
| B-7 | Кросс-сверка расхождения последнего close между провайдерами | >2% | DEGRADE |

B-1 и B-2 частично дублируют `math_firewall` (`investment_logic.py:511`, замена ±Inf → NaN
и `ffill`) — но firewall **чинит молча**, а B-* обязан **сообщить**. Это разные функции,
дублирования нет; B-2 выполняется **до** firewall, на сыром ряде провайдера.

### Блок C — достаточность для математики (профили расходятся)

| ID | Проверка | `LEGACY` | `STRICT` |
|---|---|---|---|
| **C-1** | 13 обязательных: SPY, MTUM, VLUE, QUAL, IWM, SPLV, DBC, IEF, EEM, EMB (факторы) + QQQ, AGG, URTH (бенчмарки) | BLOCK при потере `SPY.US` или всех факторов; иначе DEGRADE | BLOCK при потере любого из 10 факторов; потеря бенчмарка — DEGRADE |
| **C-2** | Эффективное окно после построчного `dropna` | BLOCK при `< max(2·K, 30)` | BLOCK при `< 252` |
| C-3 | То же окно | DEGRADE при 30–252 | DEGRADE при 252–500 |
| C-4 | Усечение окна относительно запрошенного | DEGRADE при >20%, с указанием тикера-виновника | то же |
| **C-5** | `T ≥ 3N` (наблюдения против рисковых активов) | DEGRADE | BLOCK |
| **C-6** | Ковариация положительно определена, число обусловленности в разумных пределах | DEGRADE (движок делает PSD-проекцию) | BLOCK |
| **C-7** | Рисковых позиций ≥ 2 | BLOCK | BLOCK |
| **C-8** | **Покрытие по стоимости** портфеля загруженными ценами | BLOCK при <90% | BLOCK при <90% |
| C-9 | То же покрытие | DEGRADE при 90–98% | то же |
| C-10 | Сумма весов после нормализации = 1 ± 1e-6 | BLOCK | BLOCK |
| C-11 | Все валюты позиций конвертируемы в базовую | DEGRADE, позиция помечена | то же |
| C-12 | Кэш исключён из рисковых расчётов, но учтён в знаменателе долей | BLOCK | BLOCK |
| C-13 | Наблюдений хватает для Bootstrap-CVaR | DEGRADE при <500 | то же |

**C-1 в `STRICT` после решения 2026-07-27 — реальный, а не теоретический риск.**
Раньше непрошедший C-1 означал «доберём фактор у другого провайдера». Теперь у `manual`
резерва нет (инвариант I-12), поэтому отсутствующий у Stooq факторный ETF означает,
что ручной отчёт не строится **никогда**, а не «иногда». Отсюда — проверка покрытия
вынесена вперёд, в Фазу 8 §2.5, и является гейтом запуска: чекер здесь только исполняет
решение, принятое по её результатам.

**Почему C-1 в `STRICT` не блокирует на бенчмарках.** `QQQ/AGG/URTH` объявлены
в `BENCHMARK_EXTRA` (`investment_logic.py:441-444`) и прямо помечены комментарием
«NOT used as regression factors — only for benchmark_comparison + TE». Потеря `URTH`
портит сравнение с бенчмарком, но не факторную модель. Ронять из-за неё весь отчёт —
непропорционально; задание объединяет 13 тикеров в один порог, не различая роли.

**C-8 — ключевая проверка блока.** Покрытие считается **по стоимости, а не по числу
тикеров**: портфель из 10 бумаг, где не загрузилась одна с весом 55%, имеет 90% покрытия
по счёту тикеров и 45% по стоимости. Первая метрика пропустит катастрофу, вторая остановит.

**C-12 — уточнение.** Проверять надо ровно то, что делает `analyze_all`: кэш исключён
из `actual_risky` (`investment_logic.py:1736-1739`), но его `Current_Value` входит
в `total_portfolio_value` (1717). Тест сверяет обе стороны, а не только первую.

## 4. Точка вызова

```python
report = run_checks(provider_result, positions_df,
                    profile=CheckProfile.STRICT if source == "manual"
                            else CheckProfile.LEGACY)
if report.blocked:
    raise DataQualityBlocked(report)      # токен НЕ списывается
```

Между провайдером и `analyze_all`. `DataQualityBlocked` обрабатывается в `tg_bot`
той же веткой, что и `RealPortfolioRequired`, — путь «отказ без списания» уже существует
и проверен (`tg_bot.py:2093-2108`).

**Профиль по умолчанию — `LEGACY`.** Источник, не объявивший профиль, получает мягкий:
забытый вызов не должен ужесточать поведение (I-10).

Формат отказа — человеческий, как требует §4.1 задания:

> «Не удалось загрузить цены по 2 из 8 бумаг (54% стоимости портфеля).
> Отчёт не построен, токен не списан.»

Без кодов ошибок, без `str(exc)`, без имён внутренних проверок.

## 5. Тесты — `tests/test_phase35_data_checks.py`

Каждый чекер — два кейса минимум: срабатывание и **не**срабатывание.

## 7. Риски

| Риск | Митигация |
|---|---|
| Пороги `LEGACY` подобраны «на глаз» и всё равно роняют живой отчёт | Пороги взяты **из кода**, а не назначены: `max(2·K,30)` — строка 931, `MIN_OVERLAP_TDAYS=60` — `period_returns.py:150`. Тест-гейт §5 фиксирует это на фикстурах |
| C-6 дублирует PSD-проекцию движка и конфликтует с ней | C-6 считается на **выборочной** ковариации входных доходностей, до структурной сборки. В `LEGACY` — DEGRADE, то есть проекция остаётся авторитетной |
| Блок A написан раньше своего потребителя и разойдётся с реальным Stooq | Принято сознательно: тесты на синтетических телах ответов. В Фазе 9 первый живой ответ сверяется с ожиданиями A-1…A-6, расхождения — правкой блока A |
| Рост времени отчёта | Проверки — O(T·N) по уже загруженной матрице, без сети. Замер входит в гейт Фазы 5 |
