## 1. Цель и главное отличие от задания

Три блока проверок между провайдером и `analyze_all`. Уровни: **BLOCK** — отказ,
токен не списан; **DEGRADE** — расчёт идёт, факт попадает в CoVe и `data_lineage`;
**PASS** — молча.

**Отличие от задания — профили строгости** (`README.md §2 К-4`, `PHASE_00 §3`).
Задание объявляет C-1/C-2/C-5/C-6 безусловными BLOCK для всех источников. В коде это
означало бы блокировку отчётов, которые сегодня успешно строятся:

| Что задание объявляет BLOCK | Что движок делает сегодня | Во сколько раз строже |
|---|---|---|
| C-1: потеря ≥1 фактор-ETF | `present_factors` собирается из доехавших; отказ только если не доехало НИ ОДНОГО (`investment_logic.py:903-906`) | качественно строже |
| C-2: окно < 252 наблюдений | `min_obs = max(2·K, 30)` = 30 при 10 факторах (`931`); `MIN_OVERLAP_TDAYS = 60` (`period_returns.py:150`) | ×4…×8 |
| C-6: матрица не PD | Движок делает PSD-проекцию и продолжает (`investment_logic.py:300-304`) | качественно строже |

Поэтому строгие пороги применяются к `manual` (профиль `STRICT`), а `freedom`
получает `LEGACY` — ровно те пороги, которые движок реализует сейчас. Это и есть
механизм, которым держатся **I-5, I-9 и I-10**.

## 2. Форма результата

```python
class CheckLevel(str, Enum):
    PASS = "pass"; DEGRADE = "degrade"; BLOCK = "block"

class CheckProfile(str, Enum):
    LEGACY = "legacy"    # freedom — «не хуже, чем сегодня»
    STRICT = "strict"    # manual
    DEMO   = "demo"      # витрина — не блокирует (кроме C-10/C-12)

@dataclass(frozen=True)
class CheckFinding:
    id:       str                 # "C-8"
    level:    CheckLevel
    ticker:   str | None          # None — проверка портфельного уровня
    message:  str                 # человеческий текст, БЕЗ str(exc) и без секретов
    detail:   dict                # числа для CoVe и структурного лога

@dataclass
class DataQualityReport:
    profile:  CheckProfile
    findings: list[CheckFinding]
    @property
    def blocked(self) -> bool: ...
    def user_message(self) -> str: ...      # текст отказа пользователю
    def lineage_rows(self) -> list[dict]:   # DEGRADE → строки CoVe
```

**Чекеры — данные, а не разбросанные `if`** (гейт §10 задания): каждая проверка —
запись реестра `CheckSpec(id, fn, levels: dict[CheckProfile, CheckLevel])`.
Добавление проверки = строка в реестре (проверяется `RegistryShapeTest`).

### 3.1 Почему C-2/C-3 не различаются по профилям

Пороги окна зеркалят **градуированную политику самого движка** (`PHASE_00 §3.1`),
а она одинакова для любого источника: ниже `max(2·K,30)` структурная модель не строится
физически (`investment_logic.py:930-938`), ниже 252 = `engine.trading_days` гаснет
форвардная панель (`investment_logic.py:1907-1912`, F-14). Делать `STRICT` строже
означало бы отказывать в отчёте там, где движок умеет ответить честно — на окне
100 дней он считает реализованные метрики, беты, TRC и CVaR с широкими ДИ.

Пороги 30/60 существуют **не по небрежности, а ради молодых листингов** (`SPCX` ≈ 20
торговых дней, `SKHY`) — для них минимум 30–60 дней принят сознательно. Чекер обязан
это уважать, иначе книга с недавно размещённой бумагой перестанет строиться.

Профили расходятся на **C-4**, потому что там различается ПРИЧИНА: усечение выгрузки —
это отказ источника, замаскированный под молодую бумагу (`PHASE_00 §3.3`). Для `manual`
источник один и резерва нет (I-12), поэтому «мало данных» там значит «Stooq не отдал».

**C-1 в `STRICT` после решения 2026-07-27 — реальный, а не теоретический риск.**
Раньше непрошедший C-1 означал «доберём фактор у другого провайдера». Теперь у `manual`
резерва нет (инвариант I-12), поэтому отсутствующий у Stooq факторный ETF означает,
что ручной отчёт не строится **никогда**, а не «иногда». Отсюда — проверка покрытия
вынесена вперёд, в Фазу 8 §2.5, и является гейтом запуска: чекер здесь только исполняет
решение, принятое по её результатам.

**Почему C-1 в `STRICT` не блокирует на бенчмарках.** `QQQ/AGG/URTH` объявлены
в `BENCHMARK_EXTRA` (`investment_logic.py:441-444`) и прямо помечены комментарием
«NOT used as regression factors — only for benchmark_comparison + TE». Потеря `URTH`
портит сравнение с бенчмарком, но не факторную модель. Ронять из-за неё весь отчёт —
непропорционально; задание объединяет 13 тикеров в один порог, не различая роли.

**C-8 — ключевая проверка блока.** Покрытие считается **по стоимости, а не по числу
тикеров**: портфель из 10 бумаг, где не загрузилась одна с весом 55%, имеет 90% покрытия
по счёту тикеров и 45% по стоимости. Первая метрика пропустит катастрофу, вторая остановит.

**C-12 — уточнение.** Проверять надо ровно то, что делает `analyze_all`: кэш исключён
из `actual_risky` (`investment_logic.py:1736-1739`), но его `Current_Value` входит
в `total_portfolio_value` (1717). Тест сверяет обе стороны, а не только первую.

## 3a. Предвыполненный анализ фазы (2026-07-29)

Проверка кода перед началом работ, с учётом того, что Фазы 1–2 уже выполнены.

### 3a.1 Точка вызова определена окончательно

`PHASE_00 §3c` зафиксировал разделение по доступности данных, и Фаза 2 его
подтвердила: `get_market_data` видит только матрицу цен, портфеля там нет.

| Блок | Где вызывается | Почему именно там |
|---|---|---|
| **A** (целостность выгрузки) | внутри провайдера (`fetch`) | проверяет СЫРОЙ ответ (HTTP, тело, кодировку) — за пределами провайдера этих данных уже нет |
| **B** (корректность ряда) | `get_market_data`, после провайдера | нужна только матрица |
| **C** (достаточность для математики) | слой бота, между Шагом 1 и Шагом 2 | нужны веса и стоимость портфеля: без них **C-8 физически не сможет считать покрытие по СТОИМОСТИ** и выродится в подсчёт тикеров — ровно ловушка Т-6 |

Уточнение против прежней редакции: блок A переезжает **внутрь провайдера**, а не
в `get_market_data`. Причина — после `fetch` сырого тела ответа уже не существует:
`ProviderResult` несёт разобранный `DataFrame`. A-1…A-3 (не-CSV тело, редирект,
превышение потолка) проверяемы только там, где выполняется HTTP-запрос.

### 3a.2 Профили после Фазы 2: источник известен, брать его надо у провайдера

`ProviderResult.single_source()` и `single_convention()` уже дают то, что чекерам
нужно для выбора профиля, — отдельного параметра «источник» протаскивать не надо.
Правило: `demo` → `DEMO`, `manual` → `STRICT`, остальное → `LEGACY`.

**Ловушка:** профиль должен определяться по `price_source` движка, а НЕ по
`single_source()` результата. При failover целиком по отчёту (I-13) имя провайдера
может отличаться от источника портфеля (`freedom` на резервном Stooq), а строгость
проверок задаёт именно источник ПОРТФЕЛЯ, а не то, чей фид отработал.

### 3a.3 Витрина уже неуязвима для блока C — но профиль всё равно нужен

Проверено: `DemoProvider` отдаёт все 13 обязательных инструментов и окно 1300 дней,
поэтому C-1…C-3 на витрине не сработают физически. Профиль `DEMO` тем не менее
обязателен: он страхует от будущих правок состава витрины и от C-7/C-8, которые
зависят от портфеля, а не от матрицы.

**Исключение из §3.4 в силе:** C-10 и C-12 блокируют и на витрине — это проверки
на баг в коде, а не на качество данных.

### 3a.4 Что уже есть в движке и НЕ надо дублировать

| Чекер | Уже реализовано |
|---|---|
| B-1 (дубли дат, сортировка) | `_candles_to_series`: `~index.duplicated(keep="last")` + `sort_index()` |
| B-2 (±Inf, NaN) | `math_firewall` заменяет ±Inf → NaN и делает `ffill` |
| C-2 (окно) | гейт `min_obs = max(2·K, 30)` в `calculate_structural_risk` |
| C-6 (PD-матрица) | PSD-проекция в ковариационном слое |

Чекеры не должны ПОВТОРЯТЬ эти правки — они должны **сообщать** о них.
Ключевое отличие: `math_firewall` чинит молча, а блок B обязан оставить след
в CoVe. Поэтому B-2 выполняется на СЫРОМ ряде провайдера, до firewall.

### 3a.5 Риск фазы №1 — калибровка `LEGACY`

Самое опасное в фазе — не написать чекеры, а не уронить ими живые отчёты.
Гейт `test_legacy_profile_never_blocks_current_reports` обязан прогоняться на
фикстурах РЕАЛЬНЫХ портфелей, включая разобранный в аудите: 15 позиций, плечо
1.07×, отрицательный вес кэша −7.45%, структурная нота AIX без ценовой истории,
молодой листинг SPCX. Синтетика этот класс не покрывает: например, C-10
(Σ весов = 1) на портфеле с ОТРИЦАТЕЛЬНЫМ кэшем должен проходить — сумма всё
равно 1.0, но наивная реализация «все веса ≥ 0» его завалит.

## 4. Точка вызова

```python
report = run_checks(provider_result, positions_df,
                    profile=CheckProfile.STRICT if source == "manual"
                            else CheckProfile.LEGACY)
if report.blocked:
    raise DataQualityBlocked(report)      # токен НЕ списывается
```

Между провайдером и `analyze_all`. `DataQualityBlocked` обрабатывается в `tg_bot`
той же веткой, что и `RealPortfolioRequired`, — путь «отказ без списания» уже существует
и проверен (`tg_bot.py:2093-2108`).

**Профиль по умолчанию — `LEGACY`.** Источник, не объявивший профиль, получает мягкий:
забытый вызов не должен ужесточать поведение (I-10).

Формат отказа — человеческий, как требует §4.1 задания:

> «Не удалось загрузить цены по 2 из 8 бумаг (54% стоимости портфеля).
> Отчёт не построен, токен не списан.»

Без кодов ошибок, без `str(exc)`, без имён внутренних проверок.

> списание живёт после CHECKPOINT 3.
>
> **🔴 Ловушка, найденная замером.** Наивное подключение блокировало БЫ каждого
> freedom-пользователя: `values` идут ключами ПОРТФЕЛЯ, а `data.columns` —
> РАЗРЕШЁННЫМИ, и C-8 докладывал «70% стоимости непокрыто» на здоровой книге.
> Нужен мост через `resolve_tickers`, причём с **суммированием при коллизии**:
> две неликвидные бумаги законно делят один прокси (§−38).
>
> **Калибровка C-7.** Безусловный BLOCK противоречил принципу LEGACY
> («не хуже, чем сегодня»): движок строит отчёт по книге из одной позиции.
> Стало: LEGACY/DEMO → DEGRADE, STRICT → BLOCK.

### Исходная диагностика (2026-07-30)

**`data_checks.py` не вызывается НИ ОТКУДА.** Поиск по всему `src/`:

```
grep -rn "data_checks|CheckProfile|profile_for_source|DataQualityReport" src/
→ ничего, кроме самого модуля
```

Единственный импортёр — `tests/test_phase35_data_checks.py`. Точка вызова из §4
(«между провайдером и `analyze_all`; `DataQualityBlocked` — той же веткой, что
`RealPortfolioRequired`») **не реализована**. Следствия:

- польза, заявленная в `AUDIT.md §−36` («потеря позиции весом 55% больше не
  выглядит как 90% покрытия»), **в проде не наступила**;
- `test_degrade_rows_reach_lineage` проверяет, что объект УМЕЕТ отдать строки
  lineage, а не что DEGRADE доезжает до CoVe живого отчёта — не доезжает;
- `test_block_means_token_not_charged` из §5 отсутствует и нереализуем, пока
  ветка отказа не подключена.

Модуль аккуратный и покрытый — проблема не в качестве кода, а в **незавершённой
интеграции, зафиксированной как завершённая фаза**. Подключение стоит делать до
Фазы 4: парсер ручного ввода должен опираться на эти чекеры, а не заводить свои.
