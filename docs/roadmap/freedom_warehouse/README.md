## 1. Граница проекта — что сюда НЕ входит

| Не входит | Где живёт |
|---|---|
| Ручной ввод портфеля (FSM, экран подтверждения, черновик) | `roadmap/manual_portfolio/` Фазы 04–07 |
| Источник цен для `manual` (Stooq) | `roadmap/manual_portfolio/` Фазы 08–09 |
| Налив `origin='stooq'` в витрину | **отменён как обязательный шаг** — см. §3 |

Разделение не организационное, а содержательное: у двух проектов **разные
юридические основания**. Витрина Freedom обслуживает клиента брокера его же
данными. Ручной ввод обслуживает человека, чей статус клиента неверифицируем, —
и потому не имеет права видеть ни байта данных Tradernet (I-12).

## 2. Инвариант, общий с Manual Portfolio

**I-14** («происхождение едет с данными через хранилище») определён в
**`roadmap/manual_portfolio/PHASE_00_CONTRACT.md §2`** — там, где живёт весь
юридический контракт, — и этот проект его ИСПОЛНЯЕТ, а не переопределяет.

Смысл: собственная витрина не «отмывает» источник. Строка, налитая из
Tradernet, остаётся данными Tradernet, и для `manual` запрещена так же, как сам
Tradernet. Механизм — `origin` в первичном ключе и в `WHERE`
(`PHASE_11 §0.3`, `§4.2`).

🔴 Если проекты когда-нибудь сойдутся на одной БД, I-14 — единственное, что
удерживает границу. Ослабить его нельзя ни ради удобства, ни ради
переиспользования кода.

## 3. Что изменилось после находки bulk-выгрузки Stooq (2026-08-09)

`PHASE_11` проектировался, когда Stooq предполагалось опрашивать по тикеру, и
шаг **11.7** («загрузчик Stooq в ETL, `origin='stooq'`») существовал ровно
затем, чтобы снять с горячего пути риск бана IP.

Затем выяснилось, что `stooq.com/db/` отдаёт историю целиком одним архивом.
Ручному вводу больше не нужна витрина, чтобы безопасно ходить в Stooq: ему
достаточно **файла и читателя** — без PostgreSQL, без ETL, без этого проекта
(`manual_portfolio/PHASE_08 §2.7`).

Следствия:

* **шаг 11.7 перестаёт быть обязательным** для запуска ручного ввода и
  становится опциональной оптимизацией «когда-нибудь потом»;
* **критический путь витрины укорачивается**: 11.1 → 11.2 → 11.3 → 11.4 → 11.6,
  всё для ветки `freedom`;
* **зависимость от Фазы 08 снимается** — она была нужна только шагу 11.7.

То есть разделение проектов не просто организационное: оно **разрывает
единственную связь**, из-за которой витрина ждала замера Stooq.

## 4. Порядок работ

Шаги и их обоснование — `PHASE_11_QUOTES_WAREHOUSE.md §8`. Нумерация «11.x»
унаследована от роадмапа Manual Portfolio, где витрина изначально
проектировалась; переименовывать её не стали, чтобы не рвать десятки внутренних
ссылок ради косметики.

| Шаг | Что | Дней | Ветка |
|---|---|---|---|
| 11.1 | `origin` + `corporate_actions` + миграция | 1 | `freedom` |
| 11.2 | Публичная `apply_split_conventions` в `history.py` | 0.5 | обе |
| 11.3 | `services/quotes_store.py` | 1 | `freedom` |
| 11.4 | `WarehouseProvider` + `_MANUAL_FORBIDDEN` + I-14 | 1 | `freedom` |
| 11.5 | Честный CoVe + порог свежести в торговых днях | 0.5 | обе |
| 11.6 | Гейт покрытия + failover целиком по отчёту | 1 | `freedom` |
| 11.8 | Инфраструктура: Cloud SQL, VPC, Cloud Run Job | 1 | `freedom` |
| 11.9 | Бэкфилл, сверка, включение флага | 0.5 | `freedom` |
| ~~11.7~~ | ~~Загрузчик Stooq в ETL~~ | — | **снят**, см. §3 |

Шаги 11.2 и 11.5 помечены «обе», потому что трогают общий код (`history.py`,
`data_lineage.py`). Это не возврат связанности: правки полезны обеим веткам и
ни одна из них не ждёт другую.
