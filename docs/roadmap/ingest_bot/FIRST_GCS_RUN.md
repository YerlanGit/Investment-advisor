## 0. Что здесь решается за 30 секунд

| Вопрос | Ответ |
|---|---|
| Почему нельзя просто задеплоить и слать файл? | Дефолты репозитория дают РАЗНЫЕ бакеты у писателя и читателя. Симптома нет: срезы применяются, а отчёт читает другой файл |

## 1. Кольцо «загрузчик → отчёт» — ГЛАВНОЕ

Полный путь объекта состоит из **трёх** частей, и совпасть обязаны все три:

```
                бакет                префикс   имя объекта
загрузчик ПИШЕТ gs://<_QUOTES_BUCKET>/stooq/   prices.sqlite   (QUOTES_BUCKET + QUOTES_PREFIX + DB_OBJECT_NAME)
отчёт     ЧИТАЕТ gs://<_STATE_BUCKET>/stooq/   prices.sqlite   (gcsfuse /mnt/state + STOOQ_DB_PATH)
```

**Префикс и имя пинятся тестом** (`test_object_name_matches_what_the_report_bot_reads`).
**Бакет — НЕТ**, и это сознательно: он решение владельца. Поэтому дефолты
репозитория расходятся:

| Подстановка | Дефолт |
|---|---|
| `_STATE_BUCKET` | `ramp-bot-state` |
| `_QUOTES_BUCKET` | `ramp-bot-quotes` |

🔴 **С этими дефолтами кольцо РАЗОМКНУТО.** Замкнуть — одно из двух, осознанно:

**(а) Один бакет + условие IAM** (то, что владелец выбрал в `§−100`).
В Build Trigger задать `_QUOTES_BUCKET=ramp-bot-state`, а радиус писателя
сузить условием на префикс:

```bash
gcloud storage buckets add-iam-policy-binding gs://ramp-bot-state \
  --member=serviceAccount:<INGEST_SA> \
  --role=roles/storage.objectAdmin \
  --condition=title=stooq-only,expression="resource.name.startsWith('projects/_/buckets/ramp-bot-state/objects/stooq/')"
```

Компенсирующий контроль здесь — **условие**, а не разделение бакетов. Без него
у загрузчика полный доступ к `tokenomics.db` (балансы) и `users_vault.db`
(ключи брокера).

**(б) Отдельный бакет** — тогда отчётный бот переводится на него **ОТДЕЛЬНЫМ
осознанным деплоем**. 🔴 `--set-env-vars` заменяет **ВЕСЬ** набор переменных;
эта грабля уже однажды выключила Premium V2 в проде.

**Деплой сам произносит вердикт.** Шаг `deploy-ingest-bot` печатает оба пути и
говорит `✅ КОЛЬЦО ЗАМКНУТО` либо `🔴 КОЛЬЦО РАЗОМКНУТО` — прочитайте эту
строку в логах сборки, она там ради этого.

## 2. Что должно быть заведено до деплоя

| Подстановка / секрет | Зачем | Если пусто |
|---|---|---|
| `_INGEST_SERVICE` | имя сервиса Cloud Run | шаг no-op, бот не деплоится (штатное состояние) |
| `_INGEST_SA` | **свой** сервис-аккаунт | 🔴 деплой ОТКАЗЫВАЕТ: под дефолтным Compute-SA ограничение прав существует только на бумаге |
| `_INGEST_ADMIN_IDS` | ваш Telegram-id | бот стартует, но **fail-CLOSED**: не пустит никого |
| `_QUOTES_BUCKET` | бакет базы | см. §1 — кольцо |
| `_INGEST_BOT_TOKEN_SECRET` | имя секрета с токеном | 🔴 привязка к НЕСУЩЕСТВУЮЩЕМУ секрету роняет **весь** деплой (`§−101`) |
| секрет `INGEST_TASK_TOKEN` | закрывает `POST /tasks/check` | без него плановая проверка ОТКЛЮЧЕНА |

🔴 **Токен загрузчика обязан отличаться от токена главного бота.** Один на двоих
= 409 у обоих и упавший ГЛАВНЫЙ бот (`§−99`). Бот проверяет это на старте и
отказывается подниматься — но проверка видит только то, что попало в его
окружение; гарантию даёт разный секрет, а не она.

## 3. Порядок первого запуска

1. **База должна уже лежать в бакете.** Бот её с нуля **не создаёт**: бутстрап
   из архива истории (0.84 ГБ) — операция на машине оператора. Залейте
   `prices.sqlite` в `gs://<бакет>/stooq/` до первого среза.
2. `/status` — убедиться, что бот базу ВИДИТ. В шапке теперь печатается
   **полный путь объекта** — сверьте его глазами с `STOOQ_DB_PATH` отчётного
   бота. Это то самое место, где ловится разомкнутое кольцо.
3. `/universe` — допуск C-1 с ГЛУБИНОЙ истории. Нужно `факторы 10/10 ✅`;
   наличие бары не равно пригодности, и бумага с обрывочной историей схлопывает
   окно всей панели.
4. Скачать дневной срез со `stooq.com/db/` (`YYYYMMDD_d.txt`, ≈700 КБ) и
   **переслать файл в чат**.
5. Прочитать сводку. Дальше — `/status`, чтобы увидеть новое поколение.

## 4. Как читать отказы

Три самых вероятных отказа первого запуска теперь названы по-русски (`§−103`);
до этого они утекали английским стектрейсом со ссылкой на доки Google.

| Текст в чате | Что чинить |
|---|---|
| `нет учётных данных GCP` | сервису не задан `--service-account` (подстановка `_INGEST_SA`) |
| `нет доступа к … (403)` | бакет тот, прав на объект нет → роль `objectAdmin` с условием на `stooq/` |
| `бакет или префикс не найден … (404)` | не тот бакет или префикс → сверьте `_QUOTES_BUCKET` и `QUOTES_PREFIX` |
| `в … нет prices.sqlite` | базы в бакете нет — нужен бутстрап (см. §3.1) |
| `объект изменился с поколения N (412)` | базу трогали **мимо бота**. 🔴 Это ОТКАЗ, а не повод повторить: тихий повтор затёр бы чужую запись |

**412 — единственный признак того, что в базу писал кто-то ещё.** Оператор
один по построению (`PLAN §1.2`), поэтому конфликт означает не «не повезло», а
нарушение — разберитесь, прежде чем слать файл снова.

## 5. Защиты, на которые можно положиться

Проверено прогоном (`§−103`), не обещанием:

- **Повтор идемпотентен** — тот же файл дважды не меняет базу.
- **Правило 9** — недокачанный будний файл отвергается ЦЕЛИКОМ (`0 < принято <
  порога`, порог `STOOQ_MIN_US_ROWS=5000`). Ноль US-баров = закрытый рынок, и
  поэтому праздники обрабатываются сами: список праздников не нужен.
- **Шапка проверяется** — страница капчи вместо CSV отсекается по `<TICKER>`.
- **`.zip` и чужое расширение** отвергаются БЕЗ чтения содержимого.
- **Дельта не заводит бумаг** (`allow_new=False`): в дневном срезе ~12 000
  тикеров США, состав базы определяет БУТСТРАП. Без этого различия первый же
  `apply` затащил бы 11 196 бумаг с историей в один день (`§−88`).
- **После любого отказа база цела** — цикл read-modify-write публикует только
  успешный результат, и только с совпавшим поколением (CAS).

## 6. Чего бот НЕ делает

- Не строит отчётов и не трогает токеномику.
- Не ходит в бакет с балансами и ключами брокера — ни кода, ни прав.
- Не создаёт базу с нуля и не принимает архив истории через чат (Telegram
  отдаёт боту не больше 20 МБ, архив весит 0.84 ГБ).
- Не монтирует том состояния (`--add-volume` в его шаге запрещён тестом).
