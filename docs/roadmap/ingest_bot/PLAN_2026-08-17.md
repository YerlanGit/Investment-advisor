## 1. Разбор задания

### 1.1 Что в нём уже решено кодом, а что придётся решить

| Фраза задания | Состояние |
|---|---|
| «загружает txt с дневными дельтами» | ✅ формат разобран, 9 правил фильтра измерены |
| «бот это всё чистит» | ✅ `parse_daily_file` — чистка уже написана, дописывать нечего |
| «создаёт prices.sqlite» | 🔴 **уточнение: не создаёт, а ОБНОВЛЯЕТ.** Создание = бутстрап из архива 0.84 ГБ; см. §3 |
| «обновляет базу Google Cloud онлайн» | 🟡 надо спроектировать: read-modify-write объекта GCS |
| «бот должен быть другим» | ✅ и это правильно по пяти независимым причинам — §2 |

🔴 **Единственная фактическая правка к заданию.** «Создаёт `prices.sqlite`»
неверно для дневного цикла: дневной срез содержит **только бары за один день**
по ~12 000 тикеров. Создать из него базу нельзя — истории в нём нет. База
рождается бутстрапом из архива истории и дальше только **дописывается**.

Практическое следствие: `apply_batch` вызывается с `allow_new=False`
(`stooq_ingest.py:480-533`). Состав базы определяет бутстрап; дельта лишь
дописывает бары уже отобранным бумагам. Обратное однажды уже случилось: первый
`apply` затащил в базу 11 196 бумаг с историей в один день.

### 1.2 🔴 «Оператор один» — что это меняет, а что нет

Соблазн прочитать это как «значит, можно проще» и снять защиты. Разбор по
пунктам показывает, что верно ровно наполовину.

**Снимается — координация.** Протоколы, которые синхронизируют ДВУХ людей,
для одного человека превращаются в ритуал, который он забудет:

| Было в первой редакции | Стало | Почему |
|---|---|---|
| `/freeze` перед ре-бутстрапом, `/unfreeze` после | **удалено** | лок защищает от гонки, которую один человек физически не создаёт. Настоящий риск ре-бутстрапа — не гонка, а ПОТЕРЯ ДНЕЙ, и лок её не лечит |
| повтор цикла до N раз при 412 | **удалено** | 412 при одном операторе означает нарушение инварианта. Тихо повторить — значит скрыть от него единственный признак |

**Усиливается — контроль.** Один человек означает **отсутствие второй пары
глаз**: никто не заметит, что база уехала пустой, что день пропущен, что
объём схлопнулся. Роль второй пары глаз переходит машине:

| Защита | Почему при одном операторе она НУЖНЕЕ, а не меньше |
|---|---|
| 412 как громкий отказ | единственный сигнал, что базу трогали мимо бота |
| курсор вне базы (§5.4) | без него откат базы не отличим от нормы: внутри себя откатившаяся база непротиворечива |
| `/missing` — список недостающих дат | человек не помнит, какие файлы он слал три недели назад |
| гард обвала размера | никто не отревьюит загрузку, кроме самого бота |
| напоминания (IB-7) | пропуск будних дней блокирует ручной тир через 7 календарных дней |

**Итог формулой:** у одного оператора отпадает *координация* и обостряется
*наблюдаемость*. Первая редакция плана перепутала это местами.

## 2. Почему бот ОТДЕЛЬНЫЙ — пять причин, все из кода

Владелец потребовал этого прямо. Требование верное, и вот чем оно держится.
🔴 Ни одна из причин не зависит от числа операторов — они все про процесс, а
не про людей.

| # | Причина | Факт |
|---|---|---|
| 1 | **Главный бот открывает базу `mode=ro`** | запрет технический, не договорной (`stooq_store.connect`, URI `mode=ro`). Дать ему писателя — сломать инвариант «гонок нет по построению» |
| 2 | **Память** | у главного бота `--memory=2Gi`, и её едят pandas и sklearn. `/tmp` на Cloud Run — это RAM; база 58.6 МБ + журнал в том же адресном пространстве конкурируют с отчётом |
| 3 | **Радиус поражения** | краш ingest-а положит бот, у которого `min-instances=1, max-instances=1`, то есть **всех пользователей** |
| 4 | **Права** | боту нужен read котировок; загрузчику — write. Разные сервис-аккаунты возможны только у разных сервисов |
| 5 | **Аудитория** | у главного бота `WhitelistMiddleware` **fail-OPEN** при пустом списке (`tg_bot.WhitelistMiddleware`, сегодня `tg_bot.py:3417-3427`) — сознательное решение для беты. Загрузчику нужен **fail-CLOSED**, и смешивать два разных дефолта в одном процессе нельзя |

### 2.1 Четыре варианта размещения и почему выбран второй

| Вариант | Приговор |
|---|---|
| A. Второй Dispatcher внутри главного бота | ❌ снимает причины 2–5 разом ради экономии одного сервиса |
| **B. Отдельный Cloud Run сервис, ТОТ ЖЕ образ, другой `--command`** | ✅ **принято** |
| C. Отдельный репозиторий и образ (как `freedom-etl/`) | ❌ пришлось бы копировать `stooq_ingest.py` — вторая копия, которая однажды разойдётся молча |
| D. Cloud Function на GCS-триггере (как RAG-ингест) | ❌ по адресату, а не по механике — §2.2 |

Вариант B работает потому, что `Dockerfile` заканчивается
`CMD ["python", "/app/src/entrypoint.py"]`, а Cloud Run умеет переопределять
команду при деплое. Образ уже содержит `src/`, `tests/` и все зависимости.

### 2.2 Честное сравнение с Cloud Function-триггером

Проект **уже умеет** принимать файлы через GCS-триггер: `cloud_function/main.py`
слушает бакет с банковскими PDF. Тот же приём подошёл бы и здесь — оператор
кладёт `.txt` в бакет, функция применяет.

| | Cloud Function | Telegram-бот |
|---|---|---|
| Лимит на размер файла | нет | **20 МБ** (Bot API `getFile`) |
| Ретраи | Eventarc | свои |
| Кому приходит сводка | **в логи** | **человеку, в чат, немедленно** |
| Нужен компьютер | да (консоль GCP) | нет |
| Опыт проекта | 🔴 путь оказался хрупким: регион триггера, загрузка модели, fail-soft шаг деплоя — и `entrypoint.py` получил boot-ingest как страховку | — |

**Вывод.** Бот выигрывает по адресату обратной связи, а не по механике. Это
надо признать прямо: сводка, которую видит только Cloud Logging, не заставит
оператора перекачать недокачанный файл. А правило 9 (`0 < принято < 5000` →
файл отвергнут целиком) существует ровно для того, чтобы человек **узнал** и
перекачал. При ЕДИНСТВЕННОМ операторе этот довод только крепнет: некому
заметить строку в логах вместо него.

При этом **гибрид принят**: бот кладёт полученный `.txt` в бакет как
аудит-след, и только потом применяет. След и интерактив не конкурируют.

## 3. Границы: что бот делает и чего не делает НИКОГДА

| Делает | Не делает | Почему |
|---|---|---|
| дневная дельта `YYYYMMDD_d.txt` | **бутстрап** | архив 0.84 ГБ / 11 842 файла; Bot API качает ≤ 20 МБ |
| файл истории одной бумаги (добор) | ре-бутстрап | тот же архив |
| `prune`, `verify-universe`, `/status`, `/missing` | `measure-convention`, `verify-seam` | обеим нужен архив истории |
| публикация базы в GCS | заливка собранной базы | 58.6 МБ > 20 МБ лимита |
| — | **любое чтение токеномики и vault** | §7: у сервиса нет и не будет таких прав |

🔴 **Бот никогда не создаёт базу с нуля.** Если скачанного объекта нет, он не
открывается как SQLite или в нём ноль инструментов — это **отказ с громким
сообщением**, а не «создам пустую и залью». Пустая база, уехавшая в бакет
поверх настоящей, стирает труд оператора и при этом выглядит как успешная
операция. При одном операторе это некому заметить до первого отчёта
пользователя.

## 5. Публикация базы

### 5.1 Почему не писать прямо на gcsfuse

Соблазн: у главного бота уже примонтирован том, можно открыть `prices.sqlite`
на запись и не возиться с загрузками.

**Что ломается.** SQLite поверх объектного хранилища не имеет работающих
файловых блокировок. Проект это уже знает и платит за это: `db_tokenomics`
вынужден держать `journal_mode=DELETE` и `synchronous=FULL`, потому что WAL на
gcsfuse **портит базу outright** (`-shm` требует произвольной перезаписи, а
gcsfuse отвечает `OutOfOrderError`). Для базы в 1 МБ, которая пишется редко,
это приемлемо. Для 58.6 МБ и миллиона UPSERT-ов в день — нет.

**Решение.** Файл целиком, объектом:

```
скачать prices.sqlite → /tmp    (запомнить blob.generation)
применить дельту локально        (0.2 с — замер)
загрузить обратно с if_generation_match=<generation>
```

Кэшировать скачанную базу между операциями не нужно: 58.6 МБ раз в сутки —
это секунды, а кэш добавил бы риск применить дельту к устаревшей копии.

### 5.2 🔴 412 — это громкий отказ, а не повод повторить

`if_generation_match` — compare-and-swap на уровне GCS: если между скачиванием
и загрузкой объект изменил кто-то ещё, загрузка отвергается кодом 412 и
облачная база остаётся нетронутой.

Первая редакция предлагала повторять цикл до N раз. **Это неверно при одном
операторе.** Повтор — правильное лечение конкуренции, а конкуренции здесь нет:
единственный человек не может одновременно слать файл боту и заливать базу
через `gcloud`. Значит 412 означает не «не повезло», а **«инвариант нарушен»**:
кто-то или что-то ещё пишет в бакет. Тихий повтор стёр бы единственный признак
этого события.

Правильная реакция — отказ с текстом:

```
🔴 база в облаке изменилась, пока я применял файл.
   При одном операторе такого быть не должно.
   Проверьте: не заливали ли вы базу вручную (gcloud storage cp)?
   Файл НЕ применён, база не тронута. Пришлите его ещё раз.
```

Повторная отправка безопасна: запись идёт по ключу `(instrument_id, trade_date)`
через `ON CONFLICT … DO UPDATE`, и повторное применение того же файла оставляет
базу побитово прежней (проверено тестом фазы MP-08.5).

🔴 Это и есть превращение договорённости в механизм: «не собирать базу на двух
машинах одновременно» (`OPERATOR_STOOQ §11.7`) сегодня держится на дисциплине,
CAS делает нарушение **видимым**, ничего при этом не ломая.

### 5.3 Три гарда целостности — вместо второй пары глаз

Выполняются на шаге 5, до разбора файла и до любой записи:

| Гард | Условие отказа | Что предотвращает |
|---|---|---|
| **валидность** | объект не открывается как SQLite или в нём нет `daily_bars` | публикацию мусора поверх рабочей базы |
| **непустота** | `instrument_count() == 0` | «создам пустую и залью» |
| **не откат** | `max(trade_date)` в базе **меньше**, чем в курсоре (§5.4) | тихую потерю дней после ручной заливки |

И один гард на шаге 7, после применения:

| Гард | Условие отказа |
|---|---|
| **обвал размера** | новый файл базы меньше 90 % прежнего |

Дневная дельта может только добавлять бары, поэтому база не вправе усохнуть.
Исключение — `/prune`, и там гард отключается явно, с показом `--dry-run`
первым.

### 5.4 Курсор вне базы: единственный детектор отката

Если оператор зальёт базу двухнедельной давности, внутри неё всё
непротиворечиво: календарь рынка выводится из тех же строк, что и бары, поэтому
**каждая бумага честно отрапортует свежесть 0**. Это уже известный класс
(`stooq_store.market_staleness_days` заведён именно из-за него).

Курсор в самой базе (`meta`, `ingest_runs`) откатится вместе с ней. Значит он
обязан лежать **снаружи**:

```
gs://ramp-bot-quotes/stooq/cursor.json      (единицы КБ)
{"applied_dates": [20260710, …, 20260818], "generation": "…", "at": "…"}
```

Хранится **множество применённых дат**, а не только максимум: этого требует
`/missing` (§6). Глубины 90 дат достаточно и с запасом.

🔴 **Расхождение вперёд и назад — разные события, и реакция разная:**

| Наблюдение | Смысл | Реакция бота |
|---|---|---|
| в базе есть даты, которых нет в курсоре | оператор применял через CLI — **штатный запасной путь** | молча досинхронизировать курсор, отметить в логе |
| в курсоре есть даты, которых нет в базе | база откатилась (ре-бутстрап, ручная заливка) | **тревога + список недостающих дат** |

Первая строка обязательна: если бот недоступен (деплой, сбой), оператор обязан
иметь право применить файл прежним способом (`OPERATOR_STOOQ §8`). Курсор,
считающий свой снимок единственной истиной, сломал бы запасной путь — а
запасной путь при одном операторе и есть весь резерв.

## 6. Ре-бутстрап: детекция вместо протокола

Ежедневный цикл переезжает в бота. Ре-бутстрап остаётся у оператора: архив
через Telegram не проходит.

**Дефект, который отсюда рождается.** Раз в квартал оператор пересобирает базу
из свежего архива и заливает её. Архив не содержит дней, которые бот применил
после его скачивания. Заливка **сотрёт их** — тихо, и база будет выглядеть
здоровой.

🔴 **Первая редакция лечила это протоколом `/freeze` → сборка → заливка →
`/unfreeze`. Решение неверное по двум причинам:**

1. `/freeze` — лок, а потеря дней **не гонка**: она случится и при идеально
   последовательных действиях одного человека;
2. протокол из четырёх шагов, где два — служебные команды, тот же человек
   забудет ровно так же, как забывает применять файлы (риск оценён как
   **высокий**).

**Действующее решение — обнаружение постфактум.** Оператор делает ре-бутстрап
как раньше, ничего не объявляя. При первом же обращении к боту тот сравнивает
курсор с датами в базе (`StooqStore.sessions`) и говорит:

```
⚠️ база в облаке моложе моего журнала: не хватает 6 торговых дней
   20260811 20260812 20260813 20260814 20260815 20260818
   Похоже, был ре-бутстрап. Перешлите эти файлы из applied/ — порядок
   не важен, повтор безвреден.
```

Отдельная команда `/missing` печатает тот же список по требованию.

Это работает потому, что применение **идемпотентно и коммутативно**: файлы
можно слать в любом порядке и сколько угодно раз. Ровно это свойство и делает
протокол ненужным.

## 7. Модель угроз и права

### 7.1 🔴 Отдельный бакет — самое важное решение этого раздела (находка **IB-F2**)

Сегодня `STOOQ_DB_PATH=/mnt/state/stooq/prices.sqlite`, то есть база котировок
лежит в `gs://ramp-bot-state` — **рядом с `tokenomics.db` (балансы) и
`users_vault.db` (Fernet-зашифрованные ключи брокера пользователей)**.

Сейчас это безопасно: писателя в бакете нет, файл туда кладёт человек.
**Появление сервиса-писателя меняет картину.**

🔴 **Возражение «оператор один, и у него всё равно есть доступ ко всему» —
мимо цели.** Ограничивается не человек, а **всегда работающий сервис**: у него
свой принципал, свой токен в Telegram и свой код, который человек не
перечитывает перед каждым запуском. Ошибка в путях, опечатка в префиксе или
утёкший токен бота — это события сервиса, а не человека, и радиус их поражения
не обязан включать деньги и ключи. Регламент уже кричит об этом заглавными
буквами: «эти два файла не трогать никогда — восстановления нет»
(`OPERATOR_STOOQ §11.4`).

**Решение: `gs://ramp-bot-quotes`, отдельный бакет.** Сервис-аккаунт
загрузчика получает `roles/storage.objectAdmin` **только на него**. Тогда
«не трогать» перестаёт быть просьбой и становится отсутствием права.

Цена вопроса — ноль: база 58.6 МБ, бесплатный лимит Standard в `us-central1`
5 ГБ. Главный бот монтирует второй том `--add-volume` (это дополнение к набору
томов, а не замена — в отличие от `--set-env-vars`, см. §9.2).

### 7.2 Кто имеет право говорить с ботом

Три рубежа, все fail-closed:

| Рубеж | Механизм | Дефолт при пустой настройке |
|---|---|---|
| 1 | `INGEST_ADMIN_IDS` — свой список, не общий `ADMIN_USER_IDS` | **никого** |
| 2 | middleware отбрасывает апдейт до хендлера | **никого** |
| 3 | каждая изменяющая команда сверяет ещё раз | отказ |

Сегодня в списке **ровно один идентификатор**, и это делает четвёртую защиту
бесплатной: **любое сообщение не от него — событие безопасности**, а не
опечатка. Логировать его как `WARNING` с идентификатором отправителя, а
отвечать нейтральным «неизвестная команда» — тем же приёмом, которым
`/grant` остаётся невидимым для чужих (`tg_bot.cmd_grant`).

🔴 **Копировать `WhitelistMiddleware` главного бота нельзя.** Он fail-OPEN:
«misconfiguration should fail OPEN for the beta». Для публичного продукта это
осознанный выбор; для сервиса, который пишет в базу котировок, — открытая
дверь. Свой список нужен и по второй причине: право начислять себе токены и
право менять цены — разные права, и человек, у которого есть первое, не обязан
иметь второе.

### 7.3 Недоверенный файл

Файл приходит из интернета, даже если прислал его владелец.

| Проверка | Когда | Основание |
|---|---|---|
| размер ≤ 2 МБ | **до скачивания**, по `message.document.file_size` | дневной срез 700 КБ; та же логика, что `PHASE_07 §3` |
| расширение `.txt` | до скачивания | — |
| имя вида `YYYYMMDD_d.txt` | до скачивания | из имени берётся дата для правила 1 |
| шапка `<TICKER>` и 8 колонок | при разборе | ловит скачанную HTML-страницу капчи |
| правило 9 (`0 < US < 5000`) | при разборе | ловит **недокачанный** файл — самый дорогой отказ |

Инъекция через содержимое невозможна: символ уходит в **параметризованный**
SQL, а не в строку (это уже свойство `stooq_ingest`, не новое требование).

### 7.4 Секреты

Токен второго бота — отдельный секрет в Secret Manager. Имя секрета —
`OMBRI_INGEST_BOT_TOKEN` (проект переезжает с имени RAMP на OMBRI) и задаётся
подстановкой `_INGEST_BOT_TOKEN_SECRET`, а не литералом: имя живёт в GCP, а не
в репозитории. В контейнере переменная называется `OMBRI_INGEST_BOT_TOKEN`;
прежнее имя `RAMP_INGEST_BOT_TOKEN` бот ещё принимает, но с предупреждением.
В образ секрет не попадает, в логи не печатается, в репозиторий не коммитится.

### IB-1 · `src/services/quote_publisher.py` (L1 Data) — публикация с CAS

```python
class QuotePublisher:
    def download(self, dest: Path) -> Snapshot     # (path, generation, size)
    def upload(self, src: Path, *, if_generation_match: int) -> int
    def read_cursor(self) -> Cursor | None
    def write_cursor(self, cursor: Cursor) -> None
    def archive_source(self, src: Path, name: str) -> None   # аудит-след
```

🔴 **Слой — L1 Data, а не L4.** Формально модуль похож на
`services/report_storage.py` (тоже GCS), но тот **доставляет отчёт человеку** и
потому L4. Этот кладёт данные, которые потом читает движок, — то же место в
графе, что `services/fx_feed.py`. Ошибиться здесь значит завести L4-модуль,
который вправе импортировать всё, и потерять смысл гейта `test_layering`.

* новых зависимостей нет: `google-cloud-storage` уже стоит и уже используется
  двумя модулями (`report_storage`, `entrypoint`);
* `412 Precondition Failed` возвращается вызывающему **как результат**, а не
  как исключение и не как повод для повтора (§5.2);
* отсутствие бакета / объекта → своё исключение, как `StoreUnavailable`:
  «не настроено» и «сломано» — разные состояния с разной реакцией.

**Тесты** (на подменённом клиенте, без сети): скачивание отдаёт generation ·
загрузка передаёт precondition · 412 не превращается в traceback и **не
приводит к повторной загрузке** · курсор переживает round-trip · пустой объект
курсора = «не знаю», а не «дат ноль».

### IB-2 · `src/services/quote_ingest.py` (L1 Data) — цикл применения

Здесь живёт вся логика цикла, и **ни одной строки aiogram**. Это позволит
тестировать её без бота — тот же приём, которым `analyze_all` отделён от `tg_bot`.

```python
def apply_daily(file: Path, *, actor: str) -> ApplyOutcome
def apply_history(file: Path, *, actor: str) -> ApplyOutcome   # добор бумаги
def status() -> StoreStatus
def missing_dates() -> list[int]
def prune(dry_run: bool) -> PruneResult
```

Цикл `apply_daily`:

```
1  download() → snapshot(generation)
2  гарды целостности §5.3: валидность · непустота · не откат
3  parse_daily_file(file)              # 9 правил, счётчики
4  fatal? → вернуть причину, база НЕ тронута, ничего не публиковать
5  apply_batch(conn, batch, allow_new=False)
6  гард обвала размера
7  upload(if_generation_match=snapshot.generation)
8  412 → громкий отказ (§5.2). Повтора НЕТ
9  write_cursor(), archive_source()
```

🔴 **Шаг 7 может отказать после шага 5.** Тогда локальная база изменена, а
облачная нет — и изменение потеряно, потому что следующий цикл начнётся со
скачивания. Это не дефект, а свойство read-modify-write, и его надо **сказать
человеку прямо**: «применено локально, опубликовать не удалось — пришлите файл
ещё раз». Идемпотентность делает повторную отправку безопасной; молчание
сделало бы пропущенный день невидимым.

**Тесты:** повторное применение того же файла → база побитово та же ·
недокачанный файл → база нетронута и причина названа · 412 → отказ **и ни
одной повторной загрузки** · пустая база → отказ до разбора · база откатилась →
отказ + список недостающих дат · база ушла вперёд (CLI) → курсор
досинхронизирован без тревоги · `allow_new=False` доказан: тикер вне набора не
заводится, попадает в счётчик «вне рабочего набора» · обвал размера → отказ.

**Гейт фазы:** ни один тест не ходит в сеть; `TradernetClient` не
конструируется ни разу (I-12 проверяется по факту конструирования).

### IB-7 · Напоминания (0.5 дня) — при одном операторе это не украшение

`PHASE_08B §9` оценивает «оператор забывает применять файлы» как риск **высокой**
вероятности и предлагает митигацию «видно в отчёте». Это митигация постфактум:
узнает пользователь, а не оператор. При единственном операторе резерва нет
вовсе — забыл он, значит забыли все.

Cloud Scheduler → HTTP-эндпоинт сервиса → бот пишет владельцу:

* торговый вечер, файл за сегодня не применён → напоминание;
* до блокировки ручного тира ≤ 2 дней → предупреждение с датой;
* курсор разошёлся с базой назад → тревога и список дат.

Эндпоинт закрыт OIDC-аутентификацией Scheduler-а, а не «секретным путём».

## 9. Деплой

### 9.1 Второй сервис из того же образа

```
gcloud run deploy ramp-ingest-bot \
  --image=<тот же тег, что у ramp-bot> \
  --command=python --args=/app/src/ingest_entrypoint.py \
  --min-instances=1 --max-instances=1 --concurrency=1 \
  --memory=512Mi --cpu=1 --no-cpu-throttling --no-allow-unauthenticated \
  --set-secrets=OMBRI_INGEST_BOT_TOKEN=${_INGEST_BOT_TOKEN_SECRET}:latest \
  --set-env-vars=QUOTES_BUCKET=ramp-bot-quotes,INGEST_ADMIN_IDS=<id>
```

| Параметр | Обоснование |
|---|---|
| `--min-instances=1` | long-polling: бот обязан жить между апдейтами |
| `--max-instances=1` | второй поллер того же токена получит от Telegram 409; плодить его незачем |
| `--memory=512Mi` | база 58.6 МБ в `/tmp` (RAM) + журнал + буфер загрузки. Оценка с запасом; замерить на первом прогоне |
| `--no-allow-unauthenticated` | публичный эндпоинт не нужен: polling исходящий |

**Про стоимость — честно, потому что при одном пользователе она заметнее
всего.** Long-polling требует всегда живого инстанса: сутки простоя ради
~30 секунд работы. Альтернатива — webhook и `--min-instances=0`: платится
только за вызовы, ценой публичного эндпоинта (закрывается заголовком
`X-Telegram-Bot-Api-Secret-Token`) и холодного старта.

**Рекомендация: начать с polling.** Он повторяет то, что в проекте уже

### 14.4 Что нашли мутации

Батарея из 13 мутаций поймала **две настоящие дыры** — обе в коде, который уже
был зелёным:

1. **Гард валидности проверялся не тем тестом.** Проб две (`daily_bars` и
   `instruments`), а тест бил только по второй: мутация первой пробы проходила
   незамеченной. Реальный случай, который она ловит, — база, недоделанная
   прерванным бутстрапом: законный SQLite с `instruments`, но без фактов.
   Добавлен отдельный тест.
2. **Защита монотонности поколения была НЕДОСТИЖИМА в обычном прогоне.**
   `time.time_ns()` почти всегда больше предыдущего значения, поэтому ветка
   принудительного сдвига не исполнялась, а тест лишь не падал. Добавлен тест с
   остановленными часами — так ведёт себя файловая система с грубым
   разрешением времени, ради которой ветка и написана.

Третья «выжившая» мутация оказалась дефектом самой мутации: она меняла метку
`kind` в журнале, а не поведение. Это тоже стоило теста — провенанс
(`apply` против `backfill`) теперь проверяемое свойство, а не намерение.

`brk-b.us`, и ни один наивный кандидат не совпадает (ловушка №7,
`STOOQ_CONVENTION §3.7`). Команда спрашивает базу тикером ДВИЖКА, то есть ровно
так, как спросит отчёт, и раскрывает подмену площадки, если та была.

### 15.4 Решения новых фаз

**`/prune` — единственная операция, где база уменьшается.** Гард обвала размера
к ней не применяется: `prune_thin_instruments` завершается `VACUUM`, и сжатие
файла — её работа, а не признак поломки. Гард существует для дельты, которая
умеет только добавлять.

**`/prune` без ядра НЕ запускается.** `keep` — факторные ETF в формах
источника; удалить их значит уронить допуск C-1, а с ним ручной тир целиком.
Пустой `keep` при недоступном `data_checks` — это «не знаем, что защищать», а
не «нечего защищать», и разница между ними стоит базы. 🔴 Списки при этом
РАЗНЫЕ и путать их нельзя: `/universe` спрашивает тикером движка, `prune`
сравнивает с формой источника (`AUDIT §−80`, дефект 5).

**Напоминание молчит, когда всё хорошо.** Сообщение, приходящее каждый день
независимо от состояния, перестают читать за неделю — и тогда оно не сработает
в тот единственный раз, когда было нужно. Порог берётся у
`MAX_MARKET_STALE_DAYS`, а не заводится свой: иначе бот обещал бы один срок, а
ручной тир отказывал по другому.

**Маршрут `/tasks/check` закрыт ДВАЖДЫ** — снаружи OIDC Cloud Scheduler
(сервис деплоится `--no-allow-unauthenticated`), внутри общим секретом. Без
секрета маршрут **отключён**: незакрытая ручка, шлющая сообщения владельцу, —
это канал для чужого шума в единственном канале связи оператора.

**Шаг деплоя — no-op по умолчанию.** `_INGEST_SERVICE` пуст, шаг fail-soft:
тот же приём, что у `configure-egress` и `deploy-rag-function`. Пустая
подстановка не имеет права ломать сборку главного бота, ради которой файл и
существует. Главный бот шагом не затрагивается: его `STOOQ_DB_PATH` остаётся на
`/mnt/state`, а переезд на отдельный бакет делается отдельно и осознанно —
`--set-env-vars` заменяет ВЕСЬ набор переменных.

### 15.5 Верификация

* **83 теста** (5 `skipTest` без aiogram) + `repo_hygiene` + `layering`;
* **мутационная батарея 25 из 25**. Три мутации сначала выжили: две оказались
  дефектами самих мутаций (одна била по `format_status` вместо

  искала ЗНАЧЕНИЕ `ramp-bot-state`, тогда как в YAML стоит подстановка
  `${_STATE_BUCKET}` — то есть ровно та форма, в которой её и написали бы.
  Теперь проверяются оба написания;
* `cloudbuild.yaml` разбирается как YAML, и тест пинит, что шаг выключен, а

🔴 **Полная сюита проекта по-прежнему не запускалась здесь**: в среде нет ни
pandas, ни aiogram, ни pytest. Это единственное утверждение о новом коде без

### 15.6 Что осталось

## 17. Развилка «куда бот пишет» и дефект, который её обесценивал

### 17.1 🔴 Утверждение о правах было ЛОЖНЫМ как реализовано

`§7.1` обещал: отдельный бакет → «не трогать перестаёт быть просьбой и
становится отсутствием права». Проверка шага деплоя показала, что это неправда:
**`--service-account` в нём не задавался**, а значит Cloud Run брал дефолтный
Compute-SA — тот самый, у которого уже есть `objectAdmin` на `_STATE_BUCKET`,
то есть на `tokenomics.db` и `users_vault.db`.

Ни отдельный бакет, ни условие IAM этого не меняли: сервис всё равно бежал бы с
полным доступом. Разделение существовало только в документе.

**Стало:** подстановка `_INGEST_SA`, флаг `--service-account` в деплое и
**отказ деплоить загрузчик, пока SA не задан**. Пустой SA — это не «возьмём
дефолтный», а «безопасность не настроена»; тихо взять дефолтный значит выдать
полный доступ за ограниченный. Пинится тестом, мутации 39/39.

### 17.2 Три варианта размещения базы — с ценой каждого

Вопрос владельца: «зачем новый бакет, если база и так обновлялась локально
такими же txt?» Вопрос верный, и первая редакция подавала бакет как часть
устройства загрузчика. Это неточно: **бакет не имеет отношения ни к формату
файла, ни к логике применения**. Он вытекает ровно из одного — из появления
ВСЕГДА РАБОТАЮЩЕГО ПИСАТЕЛЯ. Пока писатель человек со своими правами `gcloud`,
вопроса нет.

| Вариант | Правка прода | Радиус поражения сервиса | Когда выбирать |
|---|---|---|---|
| **0. Не разворачивать** | нет | нет сервиса | локальный цикл устраивает; бот покупает только «без компьютера» и напоминания |
| **1. Тот же бакет, свой SA + условие IAM на префикс `stooq/`** | **нет** | только `stooq/**` | быстрый запуск без переезда главного бота |
| **2. Отдельный бакет `ramp-bot-quotes`, свой SA** | второй том + `STOOQ_DB_PATH` | только свой бакет | когда переезд не жалко |

Варианты 1 и 2 дают **одинаковое** ограничение прав; разница в том, где лежит
файл и надо ли трогать главный бот. 🔴 Оба требуют своего SA — без него
ограничения нет ни в одном из них.

**Рекомендация — вариант 1.** Отдельный бакет был выбран до того, как стало
видно, что условие IAM решает ту же задачу, не двигая прод.
