### 2.2 ✅ ЗАКРЫТО Арх-2: `results{}` — контракт из 35 ключей, который читают 8 модулей

Схема живёт в **`src/finance/contracts.py`** (`AnalyzeResults`, слой L0), связь
с движком закреплена `tests/test_contracts_results.py`. Ниже — что было и
почему это стоило чинить.

Читатели (замер по обращениям к ключам, а не по совпадению строк):
`pdf_payload` (30 ключей), `ai_narrative` (16), `finance/data_lineage` (15),
`agent/advisor_bot` (6), `finance/portfolio_series` (6), `tg_bot` (6),
`agent/gatekeeper` (4), `finance/scenario_report` (4).

**Было:** ни dataclass, ни TypedDict, ни валидации. Чтобы узнать, что лежит в
`results["expected_effect"]`, надо было найти место сборки **внутри функции на
1 240 строк**. Опечатка в ключе у потребителя давала не ошибку, а тихое `None`
→ «—» в отчёте.

**Стало:** форма описана один раз, у каждого ключа — тип, назначение и
предупреждения, добытые прошлыми раундами. Тест сверяет множества по AST и
падает В ОБЕ СТОРОНЫ (ключ появился в движке, но не в контракте — и наоборот);
это проверено намеренной поломкой, а не заявлено.

**Находка попутно:** ключ **`factor_scores` не читает НИКТО** — ни `src/`, ни
тесты, ни шаблоны. Он помечен в контракте как мёртвый, но НЕ удалён: удаление
меняет контракт и это отдельное решение владельца, а не побочный эффект
типизации.

**Уточнение к плану.** Первая редакция §4 предписывала `total=False`
(«часть ключей условна»). Проверка показала обратное: у `analyze_all` РОВНО
ОДИН контрактный `return` (три остальных принадлежат вложенным хелперам),
поэтому все 35 ключей присутствуют всегда, а отсутствие данных выражается
ЗНАЧЕНИЕМ. Контракт объявлен `total=True`, и отдельный тест следит, чтобы
второй выход не появился незаметно.

**Это не теория — уже два инцидента разного класса:**

1. **R-6** (аудит 30.07): `actionPlan[].reason` вычислялся движком и **молча
   терялся** мапперами Premium; полгода объяснений не доезжало до читателя, и ни
   один тест этого не заметил — терять ключ в нетипизированном словаре разрешено.
2. **Коллизия имён `data_quality`** (замечена в строгой оценке §−52): в ОДНОМ
   пайплайне живут ДВА разных `data_quality` — `results["data_quality"]` (движок:
   находки чекеров, `{profile, findings[]}`, `investment_logic.py:3125`) и
   `payload["data_quality"]` (доля загруженных фактор-СЕРИЙ,
   `{factors_loaded, factors_total}`, `pdf_payload.py:1229`). Дефект **D-5**
   («покрытие 100%» при позиции без бет) — прямое следствие: число одного смысла
   прочитано в контексте другого. Совпадение имён никого не остановило, потому
   что ни один из двух контрактов не описан.

## 3. Целевая архитектура (поведение НЕ меняется)

### 3.1 Слои и направление импортов

Фактическая архитектура проекта — четырёхслойный конвейер с поперечным слоем
общих фактов. План §4 не вводит новых слоёв — он **делает существующие границы

      │ вызывает ↓
L3  Report     pdf_payload.py → premium_payload.py → premium_renderer.py
               html_renderer.py · ai_narrative.py · pdf_charts.py · report_mocks.py
               finance/data_lineage.py (CoVe) · finance/scenario_report.py
               (формат и вид; получает results{}, ничего не пересчитывает)
      │ читает контракт results{} ↓
L2  Engine     finance/investment_logic.py (analyze_all) · scoring*.py · stress.py
               black_litterman.py · simulate.py · regime.py · technicals.py
               period_returns.py · portfolio_series.py · factor_decomposition.py
               scenario_engine.py · inference.py · action_plan.py · data_checks.py

### Арх-3. Разрезание `analyze_all` — детальный план (единственная незакрытая фаза)

> **Статус: спроектирована, НЕ начата.** Ниже — результат сплошного анализа
> функции (не оценка на глаз): карта из 111 операторов, замер потока данных на
> каждой границе, инвентаризация скрытого состояния движка. Всё, что здесь
> написано, проверено по AST текущего кода.

#### 3.0 Что показал анализ (факты, а не намерения)

| Замер | Значение | Следствие для разреза |
|---|---|---|
| Границы функции | строки **1974–3213**, **1 240 строк** | — |
| Операторов верхнего уровня в теле | **111** | резать по ним, не внутри |
| Финальный `return` использует имён | **41** | это и есть «шов» — сборка в одном месте |
| Контрактных `return` | **1** (три остальных — во вложенных хелперах `_dq_requested_days`, `_res_key`) | ранних выходов нет; стадии не могут «выйти раньше», кроме исключений |
| Мутаций состояния объекта | **1** (`self.engine.risk_mandate`) | почти нет скрытой записи в `self` |
| Подтверждённых утечек переменных цикла между стадиями | **0** | стадии можно резать без переноса скрытого состояния |

**Ключевое наблюдение: поток данных СТРОГО НАКАПЛИВАЮЩИЙ.** Множество «живых»
переменных на границах только растёт — от 3 в начале до 34 перед сборкой.
Минимума в середине НЕТ, потому что почти всё, что посчитано, доживает до
финального словаря.

Отсюда следует главный вывод о ФОРМЕ разреза: **бессмысленно искать границы с
малой передачей — их не существует**. Правильная форма — не цепочка функций,
передающих аргументы, а стадии, дописывающие поля в один контекст:

```python
@dataclass
class _AnalysisCtx:
    """Состояние одного прогона analyze_all. Стадии ДОПИСЫВАЮТ поля."""
    df: "pd.DataFrame"
    ...                       # ~34 поля, ровно те, что читает сборка
```

Альтернатива (передавать 20–34 аргумента между методами) даёт сигнатуры, читать
которые тяжелее, чем нынешнюю простыню, — то есть ухудшает ровно ту метрику,
ради которой затевается фаза.

#### 3.0a 🔴 Скрытая связь, которую видно только замером

Помимо явных переменных, стадии общаются через **состояние движка**, читаемое
через `getattr` (обычный скан атрибутов его НЕ находит):

| Состояние | Кто ВЫСТАВЛЯЕТ | Кто ЧИТАЕТ (строка) |
|---|---|---|
| `_last_psd_repair` | `calculate_structural_risk` | 2321 |
| `_last_regression_nobs` | `calculate_structural_risk` | 2496 |
| `_last_ortho_betas` | `calculate_structural_risk` | 2662 |
| `_last_sparse_dropped` | `calculate_structural_risk` | 2934, 3004 |
| `_last_port_log_returns` | `calculate_structural_risk` | 3135 (в `return`) |
| `_last_fx_records` | `_apply_fx_conversion` (внутри загрузки цен) | конверсия строк, `fx_conversion` |

**Что это значит для фазы.** Порядок стадий задан не только явными
переменными: всё, что идёт ПОСЛЕ риск-модели, неявно зависит от того, что
`calculate_structural_risk` уже отработал и записал состояние. Перестановка
стадий или «ленивый» вызов риск-модели изменит числа МОЛЧА — тесты поймают не
всё, потому что часть этого состояния доезжает только до отдельных панелей.

**Правило фазы:** стадии выносятся строго в исходном порядке; ни одна не
перемещается относительно другой. Разрез — это переименование участков в
методы, а не перепланировка.

#### 3.0b Урок из проверки: наивный скан лжёт

Первый детектор утечек переменных цикла дал **44 «находки»**. Все оказались
ложными: он не учитывал ПОВТОРНУЮ привязку имени — `exc` связывается каждым
`except … as exc`, `_t` на строке 2260 это параметр вложенной функции, `orig`
на 2554 — цель другого цикла. Корректный детектор (учитывающий объемлющую
связывающую конструкцию) даёт **0 настоящих утечек**.

Это тот же класс ошибки, что `§−52` и первая редакция теста слоёв: **проверка
подстрокой/наивным скипом выдаёт уверенный, но неверный ответ**. Для Арх-3 это
означает: любой автоматический вывод по коду перед применением обязан быть
перепроверен вторым, независимым способом.
